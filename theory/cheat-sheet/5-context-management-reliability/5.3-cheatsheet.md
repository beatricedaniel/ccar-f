# Domain 5 · Task 5.3 — Implement Error Propagation Strategies Across Multi-Agent Systems

**Exam objective**: When a subagent fails, propagate *structured* error context up to the coordinator so it can deliberately choose to **retry, continue with partial results, or abort** — never let failures silently disappear or masquerade as complete data.

---

## Key concepts

- **Failures propagate, they don't stay local.** A subagent failure must reach the coordinator with enough information to make a decision. Getting this right needs THREE things:
  1. **Structured error context** (machine-readable, not a raw exception string)
  2. **Semantic distinctions between failure types** (access failure ≠ empty result ≠ transient)
  3. **A deliberate partial-result policy** (fail-entire vs. use-what-you-have)
- **Structured error > raw string.** The coordinator needs to know *what* went wrong, *where*, and *what state was reached* before the failure — not just "something broke."
- **Two MCP error-reporting mechanisms** (from the MCP Tool spec §7):
  - **Protocol errors** → standard **JSON-RPC errors** (`error.code`, e.g. `-32602` unknown tool, malformed request failing `CallToolRequest` schema, server errors). Clients **MAY** pass these to the LLM (recovery unlikely).
  - **Tool execution errors** → returned inside a normal tool result with **`isError: true`** (input-validation errors, business-logic errors). Clients **SHOULD** pass these to the LLM to enable **self-correction**.
- **Coordinator / subagent pattern** = the *orchestrator-workers* workflow (Building Effective Agents): a central LLM dynamically decomposes the task, delegates to workers, and **synthesizes** results. Errors surface at the synthesis boundary.
- Agents must gain **"ground truth" from the environment each step** and recover from errors; autonomous agents risk **compounding errors** — use stopping conditions (max iterations) and guardrails.

## Structured error context — the four fields (+message)

Every error crossing an agent boundary should carry:

| Field | Purpose |
|---|---|
| **`errorType`** | Machine-readable category (`access_denied`, `not_found`, `timeout`, `upstream_failure`) |
| **`sourceAgent`** | Which subagent produced the error |
| **`attemptedAction`** | The specific operation that failed (tool name, query, step label) |
| **`partialResults`** | Any data successfully collected before the failure |
| (`message`) | Human-readable detail |

> **`partialResults` is the most commonly omitted AND most valuable field.** If a subagent finished 80% before failing, discarding it forces a restart from scratch. Carry it forward so the coordinator can resume or discard.

## Patterns & when to use them

### When subagent errors bubble to the coordinator vs. handled locally
| Situation | Handle where | Action |
|---|---|---|
| **Transient** (timeout, network, `upstream_failure`) | Locally first | **Retry** (backoff); bubble up only if retries exhausted |
| **Permission / access failure** (`access_denied`) | Bubble to coordinator | **Escalate** — retrying with same credentials won't help; surface to user OR skip source with explicit annotation |
| **Validation** (`not_found`, bad input) | Locally or bubble | Fix input & retry, or **fail** that branch |
| **Business-logic error** | Bubble as `isError: true` | Coordinator/LLM decides; often self-correct or surface |
| **Empty result** (0 records, success) | Locally | **Not an error** — continue, note "zero records" |

### Access failure vs. empty result (classic trap — they LOOK identical)
- **Access failure** = denied / auth boundary / policy block → **must escalate**. Retrying won't help.
- **Empty result** = completed successfully, found nothing → **not an error**, continue normally.
- Conflating them causes: **false alarms** (empty treated as error) OR **invisible data gaps** (access failure silently treated as empty).

### Partial-result policy (K of N subagents succeed)
- **Fail entirely** — when missing subagents hold data that materially changes the answer. *Default for correctness-critical aggregations* (e.g. financial totals across accounts — 3-of-5 presented as complete is worse than an error).
- **Use what you have** — when failing subagents are supplementary/additive. *Default for best-effort enrichment.* MUST annotate: which sources succeeded, which failed, and why. Set a **`partial` flag**.
- **Never silently return partial data as if it were complete.**

### Error aggregation
- On fan-out, **collect ALL errors** into an aggregate; don't stop at the first failure.
- Run subagents in parallel where failures **don't short-circuit** each other; gather all results, *then* decide.

## Gotchas / exam traps

1. **Returning a plain string error across a boundary** — a string can't carry `errorType` / `sourceAgent` / `partialResults`; coordinator is forced into brittle text pattern-matching.
2. **Treating empty results and access failures identically** — over-alert or silently lose data.
3. **Stopping at the first subagent failure in a fan-out** — aborting `Promise.all` early on rejection hides errors from remaining agents. Collect all, then decide.
4. **Returning partial data without a `partial` flag** — a response that *looks* complete but silently drops failed sources is MORE dangerous than an explicit error.
5. **Discarding `partialResults` from a failing subagent** — throwing away intermediate progress forces a full restart.
6. `isError: true` lives **inside the tool result** (a successful JSON-RPC response), NOT in the JSON-RPC `error` object. Two different mechanisms — don't confuse them.
7. **Retrying a permission error** — never helps; it's an escalate case, not a retry case.
8. Coordinator getting a raw exception message and pattern-matching on text = anti-pattern.

## Quick reference

### Four error categories (D2/D5 canonical) → decision
| Category | Meaning | Decision |
|---|---|---|
| **Transient** | timeout, network, upstream flake | **Retry** (backoff) |
| **Validation** | bad/malformed input, not_found | Fix & retry, or **fail** branch |
| **Permission** | access_denied, auth/policy block | **Escalate** (don't retry) |
| **Business** | valid request, rule rejects it | Surface / self-correct (`isError: true`) |

*(Propagation-doc `errorType` maps: `timeout`/`upstream_failure`→transient · `not_found`→validation · `access_denied`→permission · business-logic→business.)*

### MCP tool result flags
- `isError: false` — normal/success result.
- **`isError: true`** — **tool execution error** in a valid result → send to LLM for self-correction.
- JSON-RPC `error` object (`code`, e.g. `-32602`) — **protocol error** (unknown tool, malformed request, server error).
- `resultType`: `"complete"` (done) vs `"input_required"` (`InputRequiredResult` — needs more input; retry with `inputResponses`).
- `content` (unstructured) vs **`structuredContent`** (JSON conforming to `outputSchema`).

### Error context returned to coordinator — minimum envelope
`{ errorType, sourceAgent, attemptedAction, message, partialResults? }`
plus aggregate report: `{ succeeded[], failed: AgentError[], data, partial: boolean }`

### Retry vs. escalate vs. fail — one-liner
- **Retry**: transient (timeout/upstream) — same call may now succeed.
- **Escalate**: permission/access_denied — human or higher authority needed; retry is futile.
- **Fail (abort)**: correctness-critical aggregation missing material data — an explicit error beats misleading partial data.
- **Continue**: empty result — success with zero records, not an error.
