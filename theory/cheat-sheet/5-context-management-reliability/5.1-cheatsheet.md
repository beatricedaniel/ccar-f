# Domain 5 · Task 5.1 — Manage Conversation Context to Preserve Critical Information

**Exam objective:** Curate what stays in the finite, degrading context window so critical facts survive long, multi-turn/agentic sessions.

## Key concepts
- **Context window = working memory**, not permanent memory. Finite; everything in the request counts: system prompt, all `messages` (incl. tool results, images, documents), tool definitions, AND the generated output (incl. extended thinking).
- **Domain mental model:** *Context is finite and degrades — extract facts, trim noise, verify provenance.*
- **Context rot:** as token count grows, accuracy and recall degrade. More context is NOT automatically better — curation matters as much as capacity.
- **Three failure modes that erode context:**
  1. **Progressive summarization loss** — each summary pass discards detail irretrievably; a summary of a summary flattens nuance (e.g. `{"status":"partial","retried":3,"last_error":"timeout on shard 2"}` → "the operation had some issues"). Fix: extract critical facts once from the RAW source into a structured/typed artifact and carry it forward **verbatim**. Never summarize summaries.
  2. **Lost-in-the-middle** (Liu et al., 2023) — retrieval accuracy is highest at the **start (priming)** and **end (recency)** of a long window; middle content is underweighted even though present. Fix: **restate critical constraints/facts at the point of use**, don't assume a fact from 50k tokens ago persists.
  3. **Tool output trimming** — raw tool output (API/file/DB) is far larger than needed; noise wastes tokens AND misdirects attention. Fix: trim at the boundary BEFORE it enters context — extract needed fields, truncate long lists to a sample + count, return structured summaries not raw blobs.
- **Provenance:** carry metadata with extracted facts (which tool call, timestamp, run) so later turns can assess freshness/validity.

## Patterns & when to use them
- **Extract-then-carry:** parse raw tool output → typed record (only needed fields) → pass the structured JSON into the next message, never the raw payload.
- **Restate-at-point-of-use:** prepend a `CRITICAL_CONSTRAINT` string to the current user turn when the task may touch a sensitive area — don't rely on memory of an early turn.
- **Proactive `/compact`:** invoke at **phase boundaries** (phase complete, conclusions clear), NOT reactively when the window is nearly full (that summarizes from a degraded window).
- **Server-side compaction** (API): the *primary* strategy for long-running/agentic workflows; automatically summarizes earlier conversation on the server so it can continue past the window limit. Beta for Claude 4.6+ and Mythos Preview.
- **Context editing** (finer-grained): **tool result clearing** (drop old tool results in agentic loops) and **thinking block clearing**.
- **Multi-session agents:** design state artifacts for fast context recovery on new session start (memory tool multisession pattern).

## Gotchas / exam traps
- **Summarizing summaries** is the classic wrong answer — always summarize from the ORIGINAL source once into a durable structured artifact.
- **Passing raw tool output straight into messages** = wrong. Extract minimum fields first.
- **Waiting until the window is full to `/compact`** = wrong (degraded input). Compact proactively.
- **Cached prompt prefixes STILL occupy the context window** — prompt caching changes what you *pay*, not whether tokens *count*. Input split across `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`; all three count.
- **Token count ≠ information density.** Long ≠ informative. Budget tokens for signal, not scaffold.
- **Thinking tokens count** toward the window (subset of `max_tokens`, billed as output). Whether *previous* thinking blocks stay depends on model: Opus 4.5+/Sonnet 4.6+/Fable 5/Mythos keep them; earlier Opus/Sonnet + all Haiku strip them automatically.
- **You MUST return the unmodified thinking block (with signature) alongside its `tool_result`** — the only case where you must return thinking blocks. Modifying it → cryptographic signature error.
- **Overflow:** if input alone exceeds the window → `400 invalid_request_error` ("prompt is too long") on every model. On 4.5+ models, if input+`max_tokens` exceeds window the request is accepted but generation stops with `stop_reason: "model_context_window_exceeded"`.

## Quick reference

### Context window sizes
| Models | Window |
|---|---|
| Opus 5, Opus 4.8/4.7/4.6, Sonnet 5, Sonnet 4.6, Fable 5, Mythos 5, Mythos Preview | **1M tokens** (default, no beta header, standard pricing) |
| Sonnet 4.5, Haiku 4.5, and other older models | **200k tokens** |
| Max output (1M-window models) | up to **128k output tokens** |
| Images / PDF pages per request | 600 (1M models) / 100 (200k models) |

### Context awareness (auto token-budget tracking)
- Sonnet 5, Sonnet 4.6, Sonnet 4.5, Haiku 4.5 track remaining budget; API injects `<budget:token_budget>…</budget:token_budget>` and `<system_warning>Token usage: X/Y; Z remaining</system_warning>`. You never send these.
- Opus 4.7+, Fable 5, Mythos 5 do NOT get injected tags — use explicit **task budgets** (beta) instead.

### Management levers
| Lever | What it does |
|---|---|
| `/compact` (Claude Code) | In-session summarize → replaces history with summary + fresh context; recovers budget without ending session |
| Server-side compaction (API, beta) | Auto-summarizes on server to continue past limit |
| Context editing | Tool result clearing; thinking block clearing |
| Token counting API | Estimate tokens before sending |
| Extract facts / trim tool output | Reduce noise at boundary |

### Long-context prompting tips (20k+ token inputs)
- Put **longform data at the TOP**, above query/instructions/examples.
- **Queries at the END** can improve response quality by up to **~30%** (esp. complex multi-doc).
- Wrap docs in `<document>` with `<document_content>` + `<source>` metadata subtags.
- **Ground in quotes:** ask Claude to quote relevant parts first, then answer.
