# Domain 5 · Task 5.2 — Design Effective Escalation and Ambiguity Resolution Patterns

**Exam objective:** Build explicit, deterministic, auditable escalation triggers so agents hand off to humans at the right time — neither under- nor over-escalating.

## Key concepts
- **Both directions are costly:** under-escalating causes harm; over-escalating destroys automation's value.
- **Escalate on explicit, deterministic rules — NOT vague heuristics or fluctuating model confidence scores.** A good trigger is *measurable and improvable* ("intent confidence < 0.7 after 2 clarification turns"), not *untestable* ("escalate when the agent feels unsure").
- **Three categories that reliably warrant escalation:**
  1. **Confidence thresholds** — can't resolve ambiguity after a *bounded number of clarification attempts* → stop, don't guess. Threshold is **per task type** (billing dispute tolerates far less uncertainty than a product FAQ).
  2. **Policy violations** — always route to human regardless of confidence: refund above a $ threshold, account closures, legal complaints, protected personal data. These are **rules, not judgments**.
  3. **Sensitive topics** — crisis language, self-harm, vulnerability, regulated advice (medical/legal/financial). Agent's job: **detect and route, not respond substantively**.
- **Triggers = structured conditions** evaluated at decision points in the agentic loop, each producing a **typed escalation event**.
- **Escalation hands off context, not just control.** Minimal payload: reason (which trigger fired) + conversation summary + urgency + customer's stated goal (+ attempts made, timestamp).
- **Customer preferences are a first-class input** to the escalation decision: preferred channel (chat/callback/email), sensitivity level (low/normal/high), explicit opt-outs / always-escalate topics.

## Patterns & when to use them
- **Deterministic `shouldEscalate()` order of checks** (from the reference code): customer-preference always-escalate topics → sensitive topics → policy thresholds (e.g. refund > $500) → low-confidence (< 0.7 AND attempts ≥ 2). Returns a typed trigger or null.
- **Sentiment as a soft modifier ONLY, never a primary trigger.** Escalate on *what happened* (policy threshold crossed, failed resolution attempt, explicit request), not on *how it sounded*.
- **Routing workflow** (Building Effective Agents): classify input → direct to specialized downstream prompt/tool. Good for distinct categories that are better handled separately AND when classification is accurate. Also route easy/common → cheap model (Haiku), hard/unusual → capable model (Sonnet).
- **Related agentic workflow patterns to know:** prompt chaining (fixed decomposable subtasks, gates for checks), parallelization (sectioning = independent subtasks; voting = same task multiple times / thresholds), orchestrator-workers (central LLM dynamically decomposes — subtasks NOT pre-defined), evaluator-optimizer (generate ↔ evaluate loop with clear criteria).

## Gotchas / exam traps
- **Sentiment score as the PRIMARY trigger = the top wrong answer.** Why it fails: (1) noisy — frustrated ≠ needs human; (2) latency mismatch — scores past utterances but decision must anticipate next moment; (3) adversarial brittleness — users game it by feigning frustration.
- **Escalating with only a customer ID (no context)** forces the human to re-read everything — always attach summary + goal + reason.
- **Treating escalation as failure** — it is a *designed outcome*, not an exception. Hiding escalations or retrying indefinitely causes more harm than escalating cleanly and early.
- **Single global confidence threshold** — wrong; define thresholds *per domain/task type*.
- **Ignoring customer preferences** — overriding a stated "I want a human for this" even with a correct automated answer damages trust.

## Quick reference

### Escalation trigger types → urgency
| Trigger | Fires when | Urgency |
|---|---|---|
| `CUSTOMER_PREFERENCE` | topic in customer's always-escalate list | normal |
| `SENSITIVE_TOPIC` | self-harm, legal-complaint, account-closure, regulated advice | critical |
| `POLICY_VIOLATION` | exceeds automated policy (e.g. refund > $500) | high |
| `LOW_CONFIDENCE` | intent confidence < 0.7 AND clarification attempts ≥ 2 | normal |

### Structured escalation event fields
`trigger` · `customerId` · `conversationSummary` · `customerGoal` · `attemptsMade` · `timestamp`

### Sentiment analysis — 3 reasons it's a poor trigger
Noisy signal · Latency mismatch (past-looking) · Adversarial brittleness (gameable). Use as *soft modifier* only.

### Example numeric defaults (reference code)
`CONFIDENCE_THRESHOLD = 0.7` · `MAX_CLARIFICATION_ATTEMPTS = 2` · refund policy limit `> $500`.
