# Domain 2 · Task 2.3 — Distribute tools appropriately across agents and configure tool choice

**Exam objective:** Give each agent only the tools its role requires (scoped tool access = least privilege), and use `tool_choice` to control whether/which tool Claude calls in a given turn.

## Key concepts

- **Scoped tool access = least privilege for agents.** Each agent gets ONLY the tools it needs, nothing more. A read-only research subagent must never hold `delete_record` or `send_email`. Extra tools = irreversible side effects on a misinterpreted instruction or prompt injection.
- **The tools array is the ONLY reliable enforcement boundary.** Define tools globally once, then pass a *filtered subset* per subagent. The model has zero awareness of tools not listed in its request — it literally cannot call or be tricked into calling them. Prompt instructions are NOT an enforcement boundary; the request's `tools` list is.
- **Why not give every agent every tool:** With a long tools list Claude (1) burns inference budget disambiguating irrelevant options → degraded quality, and (2) is more likely to call a plausible-but-wrong tool, especially under ambiguous instructions. Narrow tool sets = sharper, more predictable behavior.
- **`tool_choice` controls how aggressively Claude selects a tool in a turn.** Four modes: `auto`, `any`, `tool`, `none` (see table). It is orthogonal to *which* tools exist — it governs the forcing behavior.
- **Default:** when tools are provided, `tool_choice` defaults to `{ type: "auto" }`. If NO tools are provided, a tool choice of `none` uses 0 extra system-prompt tokens.
- **Steer tool use via system prompt too (auto mode):** "Use the tools to investigate before responding" (more tool use), "Always call a tool first before responding" (stronger), "Use your judgment about whether to call a tool or respond directly" (conservative). To *require* a call rather than rely on prompting, set `tool_choice` (any/tool).
- **`disable_parallel_tool_use`:** available with `auto` and `any` → caps at at-most/exactly one tool call per turn (no parallel calls). With `tool` it forces *exactly one* call of the named tool.
- **tool_choice affects preamble/chain-of-thought text:** `auto`/`none` allow Claude to emit text (reasoning/preamble). `any` and `tool` skip the preamble text and go straight to the tool call. This shows up in token tables: `auto`+`none` share a lower token count; `any`+`tool` share a higher count (e.g. Opus 4.8: auto/none = 290, any/tool = 410).
- **`strict: true`** on a custom tool definition guarantees tool-call args match your schema exactly (separate from tool_choice).
- **Agent SDK / Claude Code tool distribution:** `allowedTools` (SDK) / `tools` frontmatter field (subagents) is an allowlist; `disallowedTools` is a denylist. Same underlying mechanism as API filtering — only listed tools reach the request — but keeps intent explicit and co-located with the subagent definition.
- **Orchestrator-worker pattern:** coordinator plans/delegates (may force `plan_subtasks` or `validate_input` first), each worker subagent gets a scoped tool set (researcher = search only; writer = write only). Coordinator forces a structured first step, then switches to `auto`.
- **Subagent tool config (Claude Code):** `tools` frontmatter = allowlist; `disallowedTools` = denylist. If BOTH set, `disallowedTools` is applied FIRST, then `tools` resolves against the remaining pool; a tool in both is removed. Omitting `tools` inherits all tools available to subagents.
- **MCP-server-level patterns:** `mcp__<server>` or `mcp__<server>__*` grants/removes all tools from a server. In `disallowedTools`, `mcp__*` removes every MCP tool from any server.
- **Restrict which subagents can spawn:** `Agent(worker, researcher)` in the `tools` field = allowlist of spawnable subagent types (main thread only). Omit `Agent` entirely → can't spawn any. `permissions.deny` with `Agent(name)` blocks specific subagents (works via settings or `--disallowedTools "Agent(Explore)"`).

## Patterns & when to use them

**Which `tool_choice` mode:**
- Use **`auto`** — default; most conversational/agentic turns. Claude decides tool vs. text. Use for the bulk of an agentic loop so the model reasons freely.
- Use **`any`** — when a tool call is a *hard contract* of the turn but any of several tools is acceptable (e.g. a logging step where every response must be recorded before returning; a writer that must always persist). Prevents the model from silently answering with text.
- Use **`tool` (named)** — when a *specific* deterministic step must always run, typically the FIRST step: `validate_input` before processing, or `plan_subtasks` before a coordinator delegates. Guarantees a structured output the rest of the system depends on.
- Use **`none`** — when you must *prevent* all tool use this turn (force a pure text response even though tools are defined).

**Forced tool → then switch to auto:** Force `tool`/`any` ONLY on the guaranteed first step. After it resolves, switch back to `auto` for the remaining turns so the agent can adapt. Leaving a forced choice in place across turns prevents the model from reasoning/adapting.

**Split tools across agents vs. one agent with all:**
- **Split (scoped subagents)** when: you need to enforce tool restrictions/permissions, work is self-contained and returns a summary, or an agent's role is narrow (research vs. write). Default to splitting — it's the safety and quality win.
- **One agent / main conversation** when: task needs frequent back-and-forth / iterative refinement, multiple phases share significant context (plan→implement→test), it's a quick targeted change, or latency matters (a non-fork subagent starts fresh and must gather context).

**Subagents vs. main conversation (Claude Code):** Use subagents when task produces verbose output you don't want in main context, you want tool/permission restrictions, or work is self-contained. Use main conversation for iterative/multi-phase shared-context work.

**Multi-agent tool-distribution best practices:** design focused subagents (each excels at one task), write specific `description` fields (Claude uses them to decide when to delegate; add "use proactively" to encourage it), limit tool access (grant only necessary tools for security + focus), check project subagents into version control.

## Gotchas / exam traps

- **`any` vs `auto` (the classic trap):** `auto` = "use a tool IF you judge it necessary" (model MAY skip). `any` = "you MUST use a tool — pick one." Using `auto` when you need a guaranteed call (logging) silently lets the model skip it. `any` when the call is mandatory.
- **`tool` vs `any`:** `tool` forces ONE SPECIFIC named tool (requires `name`). `any` forces *some* tool but Claude picks which.
- **Don't leave `type:"tool"` on for more than one turn** — it blocks adaptation. Correct only for a deterministic first step; then revert to `auto`.
- **Passing the full tool list to every agent is THE most common scoping mistake** — a research agent can then trigger writes; debugging becomes tracing calls that should have been unreachable. Filter at the call site.
- **Prompt instructions are not a real boundary** — only the `tools`/`allowedTools` list is enforceable. A tool omitted from the request cannot be invoked regardless of prompt tricks.
- **`disable_parallel_tool_use` is not a tool_choice mode** — it's a modifier on `auto`/`any`/`tool`.
- **`none` with no tools = 0 extra tokens**; providing tools always adds a tool-use system prompt (per-model token cost; `any`/`tool` cost more than `auto`/`none`).
- **`allowedTools` (SDK) and `tools` (subagent frontmatter) are the same mechanism as API `tools` filtering**, not a separate security layer — the enforcement is still "only listed tools go in the request."
- **`disallowedTools` applied before `tools`** when both are present; a tool in both is removed. If a `tools` entry resolves to nothing (typo/unavailable tool), the subagent usually fails to launch with an error naming the entries.
- **`Agent(agent_type)` allowlist only applies to the main thread** (`claude --agent`). Inside a subagent definition, listing `Agent` lets it spawn (subject to depth limit) but any type list in the parentheses is ignored.
- **Built-in subagents run with restricted tool sets:** Explore = read-only (Write and Edit denied); Plan = read-only. They skip CLAUDE.md and git status for speed/cost.
- **Background subagents get a SMALLER built-in tool set than foreground** — same definition can resolve to different tools in foreground vs. background. Forks skip both filters and get the main conversation's exact tool pool.
- **Plugin subagents ignore `hooks`, `mcpServers`, `permissionMode`** frontmatter for security.

## Quick reference

### The four `tool_choice` modes

| Value | Meaning | When to use | Tool use forced? | `name` required? |
|---|---|---|---|---|
| `{ type: "auto" }` | Model decides: zero, one, or more tools, or plain text | **Default**; most conversational/agentic turns; after a forced first step | No | No |
| `{ type: "any" }` | Must call at least one tool, but model picks which | A tool call is a hard contract of the turn (e.g. mandatory logging) | Yes (any tool) | No |
| `{ type: "tool", name: "X" }` | Must call exactly the named tool | Deterministic first step (`validate_input`, `plan_subtasks`) | Yes (that specific tool) | **Yes** |
| `{ type: "none" }` | Cannot call any tool | Force a pure text response despite tools being defined | No (prevented) | No |

### Behavior details

| Aspect | auto | any | tool | none |
|---|---|---|---|---|
| Default when tools provided | ✅ | | | |
| Emits preamble / CoT text | ✅ | skipped | skipped | ✅ |
| `disable_parallel_tool_use` effect | ≤1 tool call | exactly 1 of chosen tool | forces exactly 1 | n/a |
| Relative token cost (per-model) | lower (=none) | higher (=tool) | higher (=any) | lower (=auto); 0 if no tools |

### Tool distribution controls

| Layer | Allowlist | Denylist |
|---|---|---|
| Anthropic API | `tools` array (filtered subset per agent) | — (omit from array) |
| Agent SDK | `allowedTools` | `disallowedTools` |
| Claude Code subagent frontmatter | `tools:` | `disallowedTools:` |
| Spawnable subagents (main thread) | `tools: Agent(a, b)` | `permissions.deny: Agent(name)` |
| MCP server tools | `mcp__<server>` / `mcp__<server>__*` | `mcp__<server>` / `mcp__*` |

Precedence when both set: **`disallowedTools` first**, then `tools` resolves against the remainder; a tool in both is removed.

### Orchestrator-worker example (from official objective)

| Agent | Tools (scoped) | tool_choice | Rationale |
|---|---|---|---|
| Coordinator first turn | `validate_input` only | `{ type: "tool", name: "validate_input" }` | Force deterministic validation first |
| Research subagent | `search_knowledge_base` only | `{ type: "auto" }` | Read-only; write_file excluded; Claude decides when to search |
| Writer subagent | `write_file` only | `{ type: "any" }` | Must always call a tool; pure-text responses invalid |

### Relevant SDK / Claude Code subagent frontmatter fields

`name` (req), `description` (req, drives delegation), `tools` (allowlist), `disallowedTools` (denylist), `model` (sonnet/opus/haiku/fable/full-ID/inherit; default inherit), `permissionMode`, `mcpServers`, `hooks`, `memory`, `maxTurns`, `skills`, `isolation: worktree`, `background`, `effort`. Env: `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1` (remove built-ins), `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`.
