# Domain 2 · Task 2.2 — Implement structured error responses for MCP tools

**Exam objective:** When an MCP tool fails, return the failure as a *structured, parseable result* (not an uncaught exception) that carries enough information — category, human-readable message, and retry guidance — for the model/coordinator to decide what to do next.

---

## Key concepts

- **Two distinct failure channels in MCP** — the exam's central distinction:
  1. **Protocol errors** → JSON-RPC errors (`"error"` object with numeric `code`). For things the model can't fix: unknown tool, malformed request (fails `CallToolRequest` schema), server/transport errors.
  2. **Tool execution errors** → returned *inside a successful result* with **`isError: true`** and a `content` array. For failures during the tool's own logic: input validation, business-logic failures, expired handles.
- **Why the split matters:** a tool execution error is a *valid result the model can see and react to*. A thrown exception becomes a protocol error (or crashes the call), giving the model nothing actionable. **Rule: catch errors and return `{ content: [...], isError: true }`; never let the tool throw.**
- **Client behavior (verbatim from MCP spec):** Clients **MAY** provide *protocol errors* to LLMs (less likely to lead to recovery). Clients **SHOULD** provide *tool execution errors* to LLMs **to enable self-correction**.
- **Structured error must be self-describing.** A raw stack trace or `"Something went wrong"` / `"Error occurred"` gives the model nothing. Include: **category**, **specific message**, **retryable flag**, **details** (field/resource/retryAfterMs/scope).
- **Consistent envelope.** Always include `error` on failure, always omit it on success. Don't mix a `{ data: ... }` success shape with a `{ message: ... }` error shape — the model then has to guess which it got.
- **Never leak stack traces** in error content: not actionable for an LLM, and leaks internal paths / dependency / sensitive info. Sanitize before returning.
- **`retryable` flag drives model behavior.** A *missing* `retryable` flag is treated as **non-retryable by convention** — so omitting it on a genuinely transient error makes the model give up prematurely.
- **Tool result shape (MCP `CallToolResult`):**
  - `content`: array of content items (`text` / `image` / `audio` / `resource_link` / embedded `resource`) — the **unstructured** channel.
  - `isError`: boolean; `true` = tool execution error, `false`/absent = success.
  - `structuredContent`: server-produced JSON result data conforming to the tool's `outputSchema` (the **structured** channel). *Unrelated to LLM "structured outputs" (schema-constrained generation).* For back-compat, also serialize the same JSON into a `text` content block.

---

## Patterns & when to use them

**Choose the channel:**

| Situation | Channel | How |
|---|---|---|
| Unknown/nonexistent tool name | Protocol error | JSON-RPC `error`, code `-32602` |
| Malformed request (fails request schema) | Protocol error | JSON-RPC `error`, code `-32602` (InvalidParams) |
| Bad transport / internal server crash | Protocol error | JSON-RPC `error`, code `-32603` (InternalError) |
| Input value invalid (wrong format, out of range) | **Tool execution error** | result with `isError: true` |
| Business-logic failure (resource not found, no access, rate limited, expired handle) | **Tool execution error** | result with `isError: true` |

> Heuristic: *"Could the model fix this by trying differently?"* → tool execution error (`isError: true`), so the model can see and self-correct. *"Is the request itself unroutable/malformed?"* → protocol error.

**Retry decision:**
- **Retryable** = transient; the *same* call may succeed after a delay. → Rate limits, transient network timeouts. Include a **`retryAfterMs`** hint so the model has a concrete wait target instead of guessing.
- **Non-retryable** = retrying with the *same input* reproduces the failure. → validation, auth/permission, not-found/business. Model should **stop, explain, and optionally ask for corrected input** — not loop.

**Handle-based state (stateful tools):** MCP has no protocol-level session. A call against an **expired/unknown handle** should return a *tool execution error* saying so, so the model can recover by creating a new handle.

---

## Gotchas / exam traps

- **Two competing category vocabularies — know both.** The official 2.2 objective PDF uses **validation / auth / not_found / rate_limit**. CLAUDE.md and the question bank use **transient / validation / permission / business**. They map (see Quick reference). Match whichever set the question uses.
- **`isError: true` is still a *successful* JSON-RPC response** — `result` is present, not `error`. The MCP spec example even shows `"isError": false` inside a normal `result`. Don't confuse `isError` (tool-level) with the JSON-RPC `error` object (protocol-level).
- **Throwing an exception ≠ returning an error.** An uncaught throw terminates the call with no structured info. The #1 "common mistake." Always `try/catch` → return structured `isError`.
- **Vague message trap:** `"Error occurred"` / `"Something went wrong"` are wrong answers — message must be specific enough for the model to explain the failure to a user.
- **Omitting `retryable` → model gives up.** Missing flag = non-retryable by convention; a rate-limit error without it stalls recovery.
- **Stack traces in `content` = wrong.** Developer-facing, not model-facing; sanitize/omit.
- **Protocol errors are the *weaker* recovery path.** Clients only **MAY** forward them to the model; tool execution errors are what the model **SHOULD** get for self-correction. If a question asks "how do I let the model recover?" → `isError: true`, not JSON-RPC error.
- **`structuredContent` is NOT LLM structured outputs.** It's server result data validated against `outputSchema`; unrelated to constrained model generation.
- **When `outputSchema` is defined:** servers **MUST** return conforming `structuredContent`; clients **SHOULD** validate it.

## Quick reference

### Four error categories (map both vocabularies)

| Objective PDF category | Question-bank category | Meaning | Example | Retryable? | Model/coordinator action |
|---|---|---|---|---|---|
| `rate_limit` | **transient** | Too many requests / temporary unavailability, network timeout | "Too many requests — wait before retrying" | **Yes** | Wait `retryAfterMs`, then retry same call |
| `validation` | **validation** | Malformed input / missing required field / value out of range | "Document ID must start with 'doc_'" | **No** | Fix the input, then retry |
| `auth` | **permission** | Missing/invalid credentials or scope | "You do not have read access to this document" | **No** | Escalate to user; do not loop |
| `not_found` | **business** | Requested resource doesn't exist / business rule fails | "Document 'X' does not exist" | **No** | Verify identifier / report to user |

*Approximate mapping — transient≈rate_limit (+timeouts), permission≈auth, business≈not_found/business-logic. Only the transient/rate_limit category is retryable.*

### Structured error `details` fields (from objective PDF)

| Field | Used for |
|---|---|
| `field` | which input parameter caused a **validation** failure |
| `resource` | the identifier that was **not_found** |
| `retryAfterMs` | milliseconds to wait before a retry (**rate_limit/transient**) |
| `scope` | the missing permission scope (**auth/permission**) |

### Tool execution error — canonical shape (objective PDF pattern)

```ts
function toolError(
  category: "validation" | "auth" | "not_found" | "rate_limit",
  message: string,
  details: Record<string, unknown> = {},
  retryable = false
) {
  return {
    isError: true,
    content: [
      { type: "text" as const,
        text: JSON.stringify({ error: { category, message, retryable, details } }) },
    ],
  };
}
// success shape — note: no `error`, no isError
return { content: [{ type: "text", text: JSON.stringify(doc) }] };
```

### Tool execution error — MCP wire shape

```json
{ "jsonrpc": "2.0", "id": 4, "result": {
    "content": [{ "type": "text", "text": "Invalid departure date: must be in the future." }],
    "isError": true } }
```

### Protocol error — MCP wire shape (JSON-RPC)

```json
{ "jsonrpc": "2.0", "id": 3, "error": {
    "code": -32602, "message": "Unknown tool: invalid_tool_name" } }
```

### JSON-RPC error codes (protocol errors)

| Code | Name | Typical cause |
|---|---|---|
| `-32700` | ParseError | Invalid JSON received |
| `-32600` | InvalidRequest | Not a valid Request object |
| `-32601` | MethodNotFound | Method/tool not available |
| `-32602` | InvalidParams | Invalid params / unknown tool / malformed request |
| `-32603` | InternalError | Internal server error |

### MCP TypeScript SDK specifics

- Packages (v2, 2026-07-28 spec): `@modelcontextprotocol/server`, `@modelcontextprotocol/client`. Runs on Node.js, Bun, Deno. Schemas use **Standard Schema** (Zod v4, Valibot, ArkType…).
- Server + tool registration:
  ```ts
  import { McpServer } from '@modelcontextprotocol/server';
  import { StdioServerTransport } from '@modelcontextprotocol/server/stdio';
  import * as z from 'zod/v4';
  const server = new McpServer({ name: 'greeting-server', version: '1.0.0' });
  server.registerTool('greet',
    { description: 'Greet someone by name', inputSchema: z.object({ name: z.string() }) },
    async ({ name }) => ({ content: [{ type: 'text', text: `Hello, ${name}!` }] })
  );
  ```
- **Two ways to signal failure in the SDK:**
  1. **Return** `{ content: [...], isError: true }` → tool execution error (preferred; model sees it, self-corrects).
  2. **Throw `McpError` with an `ErrorCode`** (e.g. `InvalidParams`, `MethodNotFound`, `InternalError`) → surfaces as a JSON-RPC protocol error. Use only for genuinely protocol-level problems.
- Zod input validation runs *before* your handler → schema-invalid input auto-returns a protocol-level params error; return your own `isError` for domain/business validation.

### MCP tool definition & result fields (spec §5)

- Servers with tools **MUST** declare capability `{ "capabilities": { "tools": { "listChanged": true } } }`.
- Discovery: `tools/list` (paginated, cacheable). Invocation: `tools/call`.
- Tool def fields: `name`, `title`, `description`, `inputSchema` (JSON Schema, MUST be valid object — not `null`; no-param → `{ "type": "object", "additionalProperties": false }`), optional `outputSchema`, `annotations` (treat as **untrusted** unless from a trusted server), `icons`.
- Tool result: `content[]` (unstructured) · `isError` · `structuredContent` (structured, conforms to `outputSchema`).
- Security MUSTs: validate all tool inputs, access controls, rate-limit invocations, sanitize outputs, validate results before passing to LLM, timeouts, audit logging.
