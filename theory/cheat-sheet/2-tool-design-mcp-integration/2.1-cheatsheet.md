# Domain 2 · Task 2.1 — Design effective tool interfaces with clear descriptions and boundaries

**Exam objective:** Write tool names, descriptions, and schemas that let Claude select and call the right tool unambiguously — because the name + description + parameter schema are the model's *only* guide — and scope each tool so read/write and distinct concerns stay separated.

## Key concepts

- **Tool descriptions are the LLM's only guide.** Claude sees only `name`, `description`, and the parameter schema — never your implementation, intent, or mental model. Design them like API docs for someone who cannot ask follow-up questions.
- **Description = selection mechanism.** Claude picks a tool by semantically matching the user's goal against each description. Vague → Claude guesses; precise → Claude selects correctly. Every word in the name and description is signal.
- **A good description answers three questions:**
  1. **What** does the tool do? (purpose, not implementation)
  2. **When** should it be used? (the trigger/condition)
  3. **What does it NOT do?** (explicit boundary) — most often omitted, most important for disambiguation. Use "Do NOT use this to/for X" statements.
- **Disambiguating descriptions:** when two tools handle related-but-distinct concerns, state the distinction explicitly even if redundant (e.g. `get_invoice` "Use this when you already have the invoice ID… Do NOT use this to list or search" vs `list_customer_invoices` "Use this to discover invoice IDs… Do NOT use to retrieve a single known invoice").
- **Parameter schema = extra disambiguation surface.** Name params for semantic role, not data type (`userId` not `id`, `startDate` not `date1`). In each param description: state expected format ("ISO 8601 date string, e.g. 2024-01-15"), mark optionals + explain the omitted-default effect, enumerate valid values inline when the set is small/fixed.
- **Anthropic tool definition fields:** `name`, `description`, `input_schema` (JSON Schema, `type: "object"`, `properties`, `required`). Add `strict: true` to guarantee tool calls conform exactly to your schema (strict tool use).
- **Token-efficiency:** the `tools` param (names, descriptions, schemas), `tool_use` blocks, and `tool_result` blocks all consume input tokens. Using `tools` auto-injects a tool-use system prompt (per-model token cost). More/verbose tools = more tokens on every request — but descriptions must stay precise, not terse-to-a-fault.
- **`tool_choice`** controls invocation: `{"type":"auto"}` (default, Claude decides), `any`, `tool` (force a call), `none`. Boundary is also steerable via system prompt. `disable_parallel_tool_use: true` limits to one call/turn.
- **MCP tools are model-controlled** — the LLM discovers and invokes them automatically. Each MCP tool is uniquely identified by `name` plus metadata.
- **MCP tool object fields:** `name`, `title` (human display), `description`, `inputSchema` (JSON Schema), `outputSchema` (optional), `annotations` (optional behavior hints), `icons` (optional).
- **MCP methods:** `tools/list` (discovery; supports pagination via `cursor`/`nextCursor` and caching via `ttlMs`/`cacheScope`) and `tools/call` (invocation; params `name` + `arguments`). Result carries `content[]` and `isError`.
- **`tools` capability:** servers supporting tools MUST declare it; `listChanged: true` = server emits `notifications/tools/list_changed`.
- **Structured content:** `structuredContent` field returns JSON conforming to the tool's `outputSchema`. Distinct from LLM "structured outputs." For back-compat, also return serialized JSON in a `TextContent` block. If `outputSchema` given, servers MUST return conforming results; clients SHOULD validate.
- **Namespacing:** tool-name uniqueness is scoped to a single server. Clients/proxies aggregating multiple servers MAY hit collisions and SHOULD disambiguate by prefixing names with a server identifier. Server `name` is NOT guaranteed unique — do not rely on it for disambiguation.

## Patterns & when to use them

- **Split one tool into many when:**
  - Actions have different preconditions or risk profiles (**read vs. write**).
  - Conflating them needs complex param logic (a `mode`/`action` switch).
  - One is safe to call speculatively; the other has side effects.
  - A `mode`/`action` param switching fundamentally different behaviors is a **strong signal to split** — each action deserves its own name, description, and selection logic.
- **Consolidate into one tool when:**
  - Operations are always performed together with no meaningful independent use.
  - Splitting creates artificial back-and-forth (two round-trips for one logical step).
  - The distinction would only confuse routing without improving precision.
- **Granular vs. coarse:** favor granularity where it improves *routing precision* or *safety* (separate destructive ops); favor coarseness only where independent use never happens. Never merge read + write into one tool.
- **Add examples to descriptions** for formats/ID patterns (`INV-XXXXXX, e.g. INV-004821`, `City and state, e.g. San Francisco, CA`) and enumerate small fixed value sets inline.
- **Poka-yoke (mistake-proofing):** design so wrong calls are hard — explicit boundaries ("Do NOT…"), enums instead of free strings, required fields, precise formats, and split tools so Claude cannot conflate safe vs. destructive.
- **Stateful tools:** MCP has no protocol-level session. Return an explicit **handle** (e.g. `basket_id`) from a creation tool; accept it as an argument on later calls. Handles should be opaque, authz-validated per call, bounded-lifetime, with retention stated in the creation tool's description; expired/unknown handle → tool execution error so the model recovers.

## Gotchas / exam traps

- **Description quality drives behavior more than the name.** A generic `process_data` / "Processes data" gives Claude nothing to route on — but even a good name can't rescue a vague description.
- **Omitting the boundary** is the #1 mistake — without "Do NOT use this for X," Claude uses the closest-sounding tool when ambiguous.
- **`mode`/`action: "get"|"list"|"delete"` param = anti-pattern.** It fuses N tools behind one confusing entry point. Split them.
- **Leaking implementation details** ("calls the `/v2/invoices/{id}` endpoint") describes mechanism, not purpose. Claude needs semantic meaning.
- **Over-consolidating read + write** into one tool because they touch the same resource — Claude can't reliably tell safe from destructive when they share a description.
- **Annotations are hints, NOT guarantees.** Clients MUST treat annotations as **untrusted** unless from a trusted server. `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` describe *expected* behavior — never rely on them for security/enforcement.
- **`structuredContent` ≠ LLM "structured outputs."** It's server-produced result data, unrelated to schema-constrained model generation.
- **`inputSchema` MUST be a valid JSON Schema object (not `null`).** For no-param tools use `{"type":"object","additionalProperties":false}` (recommended) or `{"type":"object"}`. Defaults to JSON Schema 2020-12 if no `$schema`.
- **`required` is an array of property names**, not a per-property flag. Omitting a property from `required` makes it optional.
- **Two error mechanisms in MCP** (don't confuse): protocol errors → JSON-RPC `error` (e.g. unknown tool, code `-32602`); tool execution errors → `result` with `isError: true` (validation, business logic). Clients SHOULD pass execution errors to the LLM for self-correction; protocol errors rarely aid recovery.
- **Anthropic API uses `input_schema` (snake_case); MCP uses `inputSchema` (camelCase).** Same JSON Schema concept, different field names.
- **`tools/list` set** MAY be empty, MAY change over time, but MUST NOT vary per-connection as a side effect of other requests; SHOULD be deterministically ordered (helps caching / prompt-cache hits).

## Quick reference

### Anthropic tool definition (API)
| Field | Meaning |
|---|---|
| `name` | Tool identifier the model calls |
| `description` | Purpose + when-to-use + boundary; primary selection signal |
| `input_schema` | JSON Schema (`type:"object"`, `properties`, `required`) |
| `strict: true` | Guarantees tool calls match schema exactly |

### MCP tool object fields
| Field | Required? | Meaning |
|---|---|---|
| `name` | yes | Unique-per-server identifier |
| `title` | no | Human-readable display name |
| `description` | yes (effectively) | What / when / not — model routing signal |
| `inputSchema` | yes | JSON Schema of parameters (valid object, not null) |
| `outputSchema` | no | JSON Schema of structured output; enables validation |
| `annotations` | no | Behavior *hints* (untrusted unless trusted server) |
| `icons` | no | Icons for UI display |

### Tool annotations (hints, not guarantees)
| Annotation | Meaning |
|---|---|
| `readOnlyHint` | Tool does not modify its environment |
| `destructiveHint` | Tool may perform destructive/irreversible updates |
| `idempotentHint` | Repeated calls with same args have no additional effect |
| `openWorldHint` | Tool interacts with an external/open world (e.g. the web) |
| `title` | Human-readable annotation title |

### MCP methods & result fields
| Item | Purpose |
|---|---|
| `tools/list` | Discover tools; `cursor`/`nextCursor` (pagination), `ttlMs`/`cacheScope` (caching) |
| `tools/call` | Invoke a tool; params `name` + `arguments` |
| `content[]` | Unstructured result (text/image/audio/resource_link/embedded resource) |
| `structuredContent` | JSON result conforming to `outputSchema` |
| `isError` | `true` = tool execution error (self-correctable by LLM) |
| `notifications/tools/list_changed` | Emitted when `listChanged: true` and tool set changes |

### Relevant JSON Schema keywords
| Keyword | Use |
|---|---|
| `type` | `"object"` at root; `string`/`number`/`boolean`/`array`/`object`/`null` for props |
| `properties` | Map of parameter name → schema |
| `required` | Array of mandatory property names |
| `enum` | Fixed set of allowed values (inline disambiguation) |
| `description` | Per-parameter contract: format, effect-when-omitted |
| `items` | Element schema for `type:"array"` |
| `additionalProperties: false` | Lock down shape; recommended for no-param tools |
| `$schema` | Schema draft; defaults to 2020-12 (draft-07 allowed if declared) |

### Error mechanisms (MCP)
| Kind | Where | Examples | LLM recovery |
|---|---|---|---|
| Protocol error | JSON-RPC `error` (e.g. code `-32602`) | Unknown tool, malformed request | Unlikely |
| Tool execution error | `result` with `isError: true` | Validation, business logic | SHOULD be provided for self-correction |
