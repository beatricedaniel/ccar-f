# Domain 2 · Task 2.5 — Select and apply built-in tools effectively

**Exam objective:** Pick the right built-in tool for each step of a codebase task so the agent completes it *within the context window and without introducing errors* — using a progressive-narrowing funnel (Glob → Grep → Read → Edit) rather than reading everything up front. (Tool descriptions are the LLM's only guide to a tool; design/prompt them like API docs — precise, prescriptive, explicit about preconditions and failure modes.)

> ⚠️ Scope note: The official 2.5 objective + reference PDF cover **Claude Code's five built-in tools** (Grep, Glob, Read, Write, Edit) and Claude Code **settings**. The exact API `type` strings the prompt asks for (`bash_20250124`, `web_search_*`, etc.) are the **Anthropic API server/client tools** — a related-but-different surface. Both are captured below; know which layer a question is asking about.

---

## Key concepts

- **Five Claude Code built-in tools** cover the full codebase lifecycle: **Grep, Glob, Read, Write, Edit**. Right tool per step is *not* a micro-optimization — it decides whether the agent finishes within the context window.
- **Incremental / progressive narrowing** ("four-step funnel") — keep context usage proportional to the task:
  1. **Glob** — broad discovery: which files exist / where they live (e.g. `**/*.ts`, `src/**/*.config.*`). No content read.
  2. **Grep** — content search: locate the exact symbol/function/variable via regex across matched files.
  3. **Read** — targeted inspection: only after you know the relevant file. Use `offset`/`limit` to read large files in sections.
  4. **Edit** — precise modification: smallest possible change. Never Write to modify an existing file unless the change spans the whole file.
- **Most common agent mistake:** trying to read the entire codebase before acting → exhausts context, frequently fails. **Always search before reading.**
- **Absolute paths required** for all file-path tools. Relative paths silently resolve against the process working directory (may ≠ project root). Confirm the absolute path before passing it.
- **Edit precondition:** the file must be **Read at least once** before Edit is valid. `old_string` must be **unique** — include ~2–3 lines of surrounding context to disambiguate.
- **Client-side vs server-side tools (API layer):** *Client-side* tools are Anthropic-**defined** (name, schema, usage pattern) but **you execute** them in your harness (Anthropic ships reference implementations). *Server-side* tools run entirely on Anthropic's infrastructure — you just declare them in `tools` and Claude handles the rest.
- **Built-in vs custom (general selection guidance):** start with **bash** for breadth (broad programmatic leverage). **Promote to a dedicated tool** when you need to gate (security/reversibility), enforce staleness checks, render custom UI, or mark parallel-safe/serialize. A dedicated tool gives the harness typed args to intercept/audit; bash gives only an opaque command string.

## Patterns & when to use them

### Claude Code five-tool decision table
| Need | Tool | Input | Use when |
|---|---|---|---|
| Search file **contents** by regex | **Grep** | pattern, optional path/glob | You know *what* you're looking for, not *where* |
| Match file **paths** by pattern | **Glob** | glob pattern, optional dir | You know the naming convention / directory structure |
| View a specific file's contents | **Read** | absolute path, optional line range (`offset`/`limit`) | You know the exact file and need to inspect it |
| Create or fully overwrite a file | **Write** | absolute path, full content | Creating a **new** file, or full rewrite **after** reading |
| Replace a string in an existing file | **Edit** | absolute path, `old_string`, `new_string` | Targeted modification to an existing file |

### Worked funnel (canonical exam example)
Update an error message when you don't know the file:
1. `Glob: "src/**/*.ts"` → 47 paths (structure, no content).
2. `Grep: pattern="unauthorized", path="src/", type="ts"` → 2 files.
3. `Read: file_path="/project/src/auth/middleware.ts", offset=45, limit=30` → find the line.
4. `Edit: old_string=..., new_string=...` → one-line change.
→ Four tool calls, zero wasted context, no ambiguity.

### API-layer tool selection (which Anthropic tool for which job)
- **Run shell commands** → **Bash** (client-executed; you run it).
- **Read/edit files** → **Text editor / str_replace** (client-executed).
- **Run code in a sandbox you don't manage** → **Code execution** (server-executed; Python 3.11, no internet).
- **Info past training cutoff / a specific URL** → **Web search / Web fetch** (server-executed, returns citations). Web fetch only fetches URLs already in the conversation.
- **Interact with a GUI/desktop** → **Computer use** (client- or server-hosted).
- **Persist state across sessions** → **Memory** (client-executed; reads/writes a `/memories` dir).
- **Many tools, few relevant per request** → **Tool search** (discovers + appends schemas; preserves prompt cache).

## Gotchas / exam traps

- **Read-before-Edit is mandatory.** Editing a file never Read in this session is invalid; Write to modify an unread file **loses existing content** (Write overwrites the *complete* file).
- **Non-unique `old_string` → Edit fails.** Add 2–3 lines of context above/below to make the match unique.
- **Don't Write to make a one-line change.** Write = create/full-overwrite only; Edit = targeted change.
- **Glob too broad** (`**/*` on a monorepo) returns thousands of paths. Scope to a subdir or extension.
- **Grep too broad** (e.g. `"error"` across the whole repo) is a distractor "wrong" answer — narrow the pattern/path/type.
- **Reading before searching** = the classic anti-pattern. Grep to find the line number *first*, then Read with `offset`/`limit`.
- **Relative paths** silently resolve against cwd, not project root — always absolute.
- **Client vs server tool confusion:** Bash + Text editor + Memory + (self-hosted) Computer use = **client-executed** (you handle the `tool_use`). Web search, Web fetch, Code execution = **server-executed** (no client loop). Computer use can be either.
- **Anthropic-defined tools are schema-less** — declare by `type` + `name` only, no `input_schema`. A custom tool you name `"bash"` is *not* the built-in bash.
- **`name`/`type` must match as a pair.** e.g. `text_editor_20250728` pairs with `str_replace_based_edit_tool`; using it with the old name `str_replace_editor` (which belongs to `text_editor_20250124`) → 400.
- **Server-tool errors return HTTP 200**, not exceptions — an error block (`{error_code: ...}`) inside the tool_result.
- **`tool_choice` interaction:** `{"type":"auto"}` (default) / `{"type":"any"}` (must use ≥1 tool) / `{"type":"tool","name":...}` (forced) / `{"type":"none"}`. Add `"disable_parallel_tool_use": true` to cap at one tool per turn. Forcing a `tool_choice` is **incompatible with programmatic tool calling** and with `strict: true`.
- **Same principles govern MCP tool descriptions and built-in tool selection** (see 2.1). Tie back to Lesson 2.1 (Tool Description Design) and 2.4 (Context Window Management).

### `tool_choice` enum
`auto` (default) · `any` · `tool` (forced, `{type:"tool",name}`) · `none` — plus `disable_parallel_tool_use: true`.

### Token / pricing notes
- **Code execution:** free when used with web search/fetch; otherwise **$0.05/hr** after **1,550 free hours/month/org**. Containers persist 30 days, reusable.
- **Prompt caching:** cache **reads ≈0.1×** base input; **writes 1.25×** (5-min TTL) / **2×** (1-hr TTL). Adding/removing/reordering tools invalidates the cache (tools render at prefix position 0). **Tool search** appends schemas instead of swapping → preserves cache.
- **Context proportionality (the whole point of 2.5):** every unnecessary Read/Glob-dump is billed input tokens and crowds the window — the funnel keeps `input_tokens` proportional to the task.

### Client-side vs server-side (memorize)
- **Client-executed (you run it):** Bash, Text editor, Memory, self-hosted Computer use.
- **Server-executed (Anthropic runs it):** Web search, Web fetch, Code execution, Tool search, Advisor.
- **Either:** Computer use.

## Claude Code settings & precedence (from the reference PDF)

*This is the actual content of the "built-in tools reference" PDF — Claude Code settings, not API tools. Dense recap:*

**Settings files & scopes (each is a level in the stack):**
| Scope | File / source | Applies to |
|---|---|---|
| Managed settings | `managed-settings.json`, MDM policy, or claude.ai console (server-managed) | Your organization |
| Command line | `claude --settings <file-or-json>` | You, this session |
| Project local | `.claude/settings.local.json` | You, this project |
| Shared project | `.claude/settings.json` | Everyone in the project |
| User | `~/.claude/settings.json` | You, every project |

**Precedence stack (highest → lowest):** **Managed → Command line → Project local → Shared project → User.** A key set at a higher level **overrides** the same key anywhere below it.

- **Env vars aren't a level** — resolved **per key-pair**, not by stack position. `ANTHROPIC_MODEL` (shell) overrides the `model` key from any file; `ANTHROPIC_DEFAULT_MODEL` applies **only when no file sets `model`**. An `env` block *inside* a settings file is an ordinary key and follows the levels above.
- **Lists merge, scalars override.** Same list key in multiple files (e.g. `permissions.allow`) → files **combine** entries (each file adds without removing another's). Contrast: scalar keys take the single highest-precedence value.
  - **Merge exceptions (model lists):** `fallbackModel` (ordered chain — whole value from the highest file that defines it), `modelPicker` (whole list from highest *managed* source; ignores project/local; needs CC v2.1.242+), `availableModels` (managed list applied as-is; never merges across managed sources).
- **Exceptions to managed precedence (security-sensitive — a stricter/lower value wins over managed):** `disableClaudeAiConnectors`, `enableArtifact`/`disableArtifact`, `isolatePeerMachines`, `remoteControlAtStartup`, `crossSessionInbound`, `useAutoModeDuringPlan`. (Managed normally wins — these keys are the carve-outs where the *restrictive* value is honored from any/lower scope.)
- **Permission-rule combining:** `allow` never outranks an `ask` from a project/managed file; `deny` and `ask` apply immediately, `allow`/`additionalDirectories`/most `env` wait until the teammate **trusts the folder**.

**Commands / diagnostics:**
- **`/status`** — see which files loaded and which source set each key (start here when a setting "doesn't apply").
- **`claude doctor`** — per-error details; a `-p` run silently skips broken files/values (then `claude doctor` shows what it dropped).
- **`/config`** — change a setting; on the web it opens the Claude Code section of claude.ai settings rather than editing a value.

**Cloud sessions** (`--cloud` / web) run on a fresh clone: **shared project settings ARE read** (part of the clone); **user + project-local are NOT** (stay on your machine); managed applies only via **server-managed settings**. Set a cloud value via env var or by committing to `.claude/settings.json`.

**Troubleshooting "a value I set is ignored":** a higher level set it (check the stack), a flag/env var overrode it per-key, a security key kept its strict value, or the file is broken (invalid JSON → whole file/entry skipped).
