# Domain 4 · Task 4.1 — Design Prompts with Explicit Criteria to Improve Precision

**Exam objective:** Replace vague, subjective prompts with explicit, enumerated criteria and specified output formats so Claude's output is repeatable, evaluable, and low-noise.

## Key concepts
- **Vague prompts delegate the definition of quality to Claude** ("review this code", "find issues"). The model forms its own interpretation → output varies between runs, drifts across models/versions, is hard to parse or act on.
- **Explicit criteria = objective enumeration.** Instead of "find problems", say "check for SQL injection, XSS, and missing authentication."
- **Three benefits of explicit criteria:**
  1. **Repeatability** — same criteria → same *kind* of output on same input.
  2. **Evaluability** — you measure whether Claude found what you defined, not the quality of an opinion.
  3. **False-positive management** — precise scope stops Claude flagging style as security bugs, or perf notes as correctness bugs.
- **The False Positive Problem:** under-specified prompts are the root cause. False positives are expensive — block deploys, page on-call, erode trust, exhaust reviewers. A criteria list constrains the search space; Claude still applies judgment *within* each criterion but does not invent new categories.
- **Enumerated criteria list = the most reliable pattern:** numbered/bulleted named checks, each with a definition. A good definition answers *what a positive finding looks like* AND *what it does not look like* (negative examples).
- **Domain mental model (memorize):** *Specificity beats vagueness. Examples beat instructions. Schemas beat parsing.*
  - Specificity: name the thing to check, not the class of things.
  - Examples: show what a finding looks like before asking for findings.
  - Schemas: for structured output, provide a JSON schema rather than asking Claude to invent a format.
- **Golden rule (clear & direct):** Show your prompt to a colleague with minimal context; if they'd be confused, Claude will be too. Think of Claude as a brilliant but new employee lacking context on your norms.
- **Add context/motivation** behind instructions (explain *why*) — Claude generalizes from the explanation and delivers more targeted responses.
- If you want "above and beyond" behavior, **explicitly request it** — don't rely on the model inferring it from a vague prompt.

## Patterns & when to use them
- **Named criteria + definition + `notThis` (negative example)** — the primary lever for false-positive reduction. e.g. `SQL_INJECTION`: user input concatenated into SQL without parameterization; *notThis:* ORM with bound params.
- **Separate severity from category** — define the criterion first, then rules for assigning severity within it (SQL injection in a public endpoint = critical; in admin-only route = high).
- **Embed a JSON schema in the prompt (or use `response_format`)** and parse the JSON block when you need structured, automatable output. Free-form prose is for human readers only.
- **`criteriaChecked` field** — have Claude echo the list of criteria it checked, to confirm it didn't silently skip one.
- **Provide steps as numbered lists/bullets** when order or completeness of steps matters.
- **Tell Claude what TO do, not what NOT to do** (e.g. "write flowing prose paragraphs" beats "do not use markdown").
- **Match your prompt style to desired output** — removing markdown from your prompt reduces markdown in the output.
- **Structure with XML tags** (`<instructions>`, `<context>`, `<input>`, `<example>`, `<documents>`) to disambiguate mixed content; use consistent descriptive names; nest for natural hierarchy.
- **Long-context (20k+ tokens):** put longform data/documents at the TOP, above query/instructions/examples. Queries at the END can improve response quality by up to ~30% on complex multi-document inputs. Wrap docs in `<document>` with `<document_content>`/`<source>` subtags. Ask Claude to ground answers by quoting relevant parts first.

## Gotchas / exam traps
- **Category names WITHOUT definitions still delegate interpretation** ("check for injection vulnerabilities" is not explicit). Define which APIs/patterns/context makes it a positive.
- **Omitting negative examples** — telling Claude what a finding *looks like* is necessary but NOT sufficient; you must also say what does NOT qualify.
- **Too many criteria** — more than ~8–10 in one prompt dilutes attention and causes overlooked items. Group into sub-prompts / batch reviews (chain prompts).
- **Asking for free-form output then trying to parse it** — fragile. Provide a schema instead.
- **Conflating severity with criterion** — they are separate axes.
- **Prefilling is NOT supported on Claude 4.6+ and Mythos Preview** (returns 400). Use Structured Outputs or system-prompt instructions instead. (For guaranteed JSON schema conformance, use Structured Outputs, not prompt tricks.)
- Distractor: "raise `effort` to make Opus 5 shorter/longer" — Opus 5 verbosity does NOT reliably change with effort; prompt explicitly for conciseness.

## Quick reference
| Technique | Use when |
|---|---|
| Specify exact output format (JSON/XML/template) | Every consistency task |
| Enumerated criteria + `notThis` | Reduce false positives, scope reviews |
| Embed JSON schema / `response_format` | Automated pipelines |
| Structured Outputs (feature) | **Guaranteed** JSON-schema conformance |
| Prefill assistant turn | Legacy only (≤4.5) — bypasses preamble; unsupported 4.6+ |
| Retrieval grounding | Chatbots, knowledge bases (fixed info set) |
| Prompt chaining / sub-prompts | Complex or >8–10 criteria tasks |
| System prompt role | Role/character consistency |

**Consistency techniques (docs):** specify format · prefill (legacy) · constrain with examples · retrieval grounding · chain prompts · keep-in-character (system-prompt role + scenario list).

**Mnemonic:** *Specificity beats vagueness. Examples beat instructions. Schemas beat parsing.*
