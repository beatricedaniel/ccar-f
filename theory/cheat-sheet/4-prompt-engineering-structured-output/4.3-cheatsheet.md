# Domain 4 · Task 4.3 — Enforce Structured Output Using Tool Use and JSON Schemas

**Exam objective**: Guarantee typed, validated structured output from Claude by defining a "capture" tool with a JSON-Schema `input_schema` and forcing it via `tool_choice: {"type": "tool", "name": "..."}` — schemas beat parsing.

---

## Key concepts

- **Mantra**: *Specificity beats vagueness. Examples beat instructions. Schemas beat parsing.* Prompting "respond in JSON" is brittle — Claude may add prose, wrap output in markdown fences, or drop optional fields. Structure enforced by the **API** doesn't drift the way prompt instructions do.
- **Tool use = structured-output mechanism**. A tool need not do anything external. Define a tool whose sole job is to **receive** structured data. Claude fills the parameters per your schema; you read the `tool_use` block — no `JSON.parse`, no regex.
- **Inverted framing**: not "here is a function Claude can call," but "here is a typed slot Claude must fill."
- **Anatomy of a tool definition** (`tools` array, top-level param):
  - `name` — must match regex `^[a-zA-Z0-9_-]{1,64}$`
  - `description` — detailed plaintext: what it does, when to use it, what each param means. Aim 3–4+ sentences. Most important factor in tool performance.
  - `input_schema` — a **JSON Schema object** defining expected parameters.
  - `input_examples` (optional) — array of example input objects; each must be valid vs `input_schema` (invalid → 400).
  - Other optional props: `strict`, `cache_control`, `defer_loading`, `allowed_callers`.
- **Single source of truth**: define shape once in Zod → `zodToJsonSchema()` → becomes both the wire-format `input_schema` AND runtime validation (`safeParse`) → TS types via `z.infer`.
- **Response shape**: `tool_use` block has `type`, `id` (e.g. `toolu_...`), `name`, `input`. With forced tool use the block is guaranteed present.

## Patterns & when to use them

### 1. Forcing tool use to enforce structured output (the core pattern)
Set `tool_choice: {"type": "tool", "name": "capture_x"}` so Claude **must** call exactly that tool and cannot fall back to free text. Then extract the `tool_use` block and `safeParse` its `input`.
- Use whenever you need *guaranteed* structure (classification, extraction, scoring).
- With `any` or `tool`, the API prefills the assistant turn → Claude emits **no** leading natural-language text before the `tool_use` block, even if asked.

### 2. JSON Schema constraints (design the schema like a public API)
- **Enum constraints** — fixed value set → `"enum": ["low","medium","high"]`; stops invented values like "moderate"/"elevated". (Zod: `z.enum([...])`.)
- **Nullable / optional fields** — `"type": ["string","null"]` (Zod `.nullable()`) signals a missing value is *valid and expected*, not an error.
- **required array** — list fields you always need; anything absent may be omitted — design downstream code accordingly.
- **Descriptions on every field** — read by the model when populating; treat as contracts (specify format, units, ranges inline).

### 3. zod-to-json-schema (bridge Zod → JSON Schema)
- `zodToJsonSchema(schema)` or `zodToJsonSchema(schema, "MyName")` (name → nests under `definitions` + `$ref`).
- Converts types, string/number/array length checks, string patterns; resolves recursive schemas with internal `$ref`s.
- npm `v3.25.2`; **deprecated Nov 2025** — Zod v4 natively generates JSON schemas. As of v3.25 you can use Zod v4 as a peer-dep if still passing v3 schemas.
- Key options (2nd arg): `target` (`jsonSchema7` default | `jsonSchema2019-09` | `openApi3` | `openAi`), `$refStrategy` (`root` default | `relative` | `seen` | `none`), `definitionPath` (`definitions` default | `$defs`), `nameStrategy` (`ref` | `title`), `errorMessages`, `markdownDescription`, `override`/`postProcess` callbacks.
- **additionalProperties**: default set to `false` (mirrors Zod stripping unknown keys). Allow extras via `removeAdditionalStrategy: "strict"` or `.passthrough()`. `.strict()`→`false`, `.passthrough()`→`true`.

### 4. Single-tool trick vs. multiple tools
- **One capture tool** = clean typed slot for one output type.
- **Different structures per context** → define **separate tools** and pick with `tool_choice`. Avoid one monolithic tool with a union schema (pushes conditional complexity into schema + code).

### 5. Guaranteed conformance: `strict: true`
Combine forced tool use with `strict: true` on the tool definition to guarantee both *a tool is called* AND *inputs strictly match the schema* (schema-validated tool calls).

## Gotchas / exam traps

1. **`tool_choice: "auto"` for structured output** — WRONG. Claude may reply in plain text when the answer seems obvious. Use `{"type":"tool","name":"..."}`.
2. **Forgetting `nullable` on optional fields** — marking a field non-required but asserting presence in code breaks when the model omits it. Use `.nullable()` and handle `null`.
3. **Overly broad `string` for constrained values** — use `z.enum()` / JSON `enum` so the constraint is explicit to the model AND enforced at validation.
4. **Skipping validation after capture** — don't trust `tool_use.input` blindly; always `safeParse` and handle failure. Model behavior can vary.
5. **"respond in JSON" in the system prompt alongside a schema** — redundant, adds noise, can conflict. Let schema + `tool_choice` do the work.
6. **Monolithic capture tool for multiple output types** — use separate tools instead.
7. **`any`/`tool` suppress natural-language preamble** — if you need explanation *and* a tool, use `tool_choice:{"type":"auto"}` + explicit user instruction ("Use the get_weather tool in your response.").
8. **Extended thinking incompatibility** — with **manual** extended thinking (`thinking:{type:"enabled"}`), `any` and `tool` are NOT supported (error). Only `auto` (default) and `none` work. *Adaptive* thinking (on by default, e.g. Opus 5) DOES support forced tool use.
9. **Claude Mythos Preview** does not support forced tool use — `any`/`tool` → 400. Use `auto`/`none` + prompting.
10. **Prompt caching**: changing `tool_choice` invalidates cached *message* blocks (tool defs + system prompt stay cached; messages reprocessed).
11. **`input_examples` not supported** on server tools (web search, code execution) or the computer-use/browser-use toolsets; costs ~20–50 tokens (simple) / ~100–200 (nested).
12. **zod-to-json-schema `.transform()`** — JSON schema reflects the *input* side, not the transformed output; use `effectStrategy:"any"` if it breaks.

## Quick reference

**`tool_choice` — four modes**
| Value | Behavior |
|---|---|
| `{"type":"auto"}` | Claude decides whether to call any tool. **Default when `tools` provided.** |
| `{"type":"any"}` | Must call *at least one* tool (not a specific one). |
| `{"type":"tool","name":"X"}` | Must call *exactly* tool X. ← **structured output** |
| `{"type":"none"}` | No tools. Default when no `tools` provided. |

*(`auto` also accepts `"disable_parallel_use": true` to cap at one tool call/turn.)*

**Force a specific tool (Python)**
```python
response = client.messages.create(
    model="claude-opus-4-5", max_tokens=1024,
    tools=[capture_tool],
    tool_choice={"type": "tool", "name": "capture_sentiment"},
    messages=[...],
)
```

**`input_schema` — JSON Schema fields**
`type` (`object`) · `properties` · `required` (array) · `description` (per-field) · `enum` (fixed values) · `type: ["string","null"]` (nullable) · `additionalProperties` (false by default via zod-to-json-schema).

**Zod → capture tool**
```ts
const S = z.object({
  sentiment: z.enum(["positive","negative","neutral"]).describe("..."),
  confidence: z.number().min(0).max(1).describe("0.0–1.0"),
  summary: z.string().nullable().describe("... or null"),
  topics: z.array(z.string()).describe("..."),
});
type T = z.infer<typeof S>;                         // TS type
const tool = { name:"capture_sentiment", description:"...",
  input_schema: zodToJsonSchema(S) };               // wire format
// after call:
const b = res.content.find(x => x.type === "tool_use");
const parsed = S.safeParse(b.input);                // runtime validation
```
Zod methods: `z.object` · `z.enum` · `z.number().min().max()` · `z.string()` · `.nullable()` · `.array()` · `.describe()` · `z.infer<typeof S>` · `.passthrough()` / `.strict()` (additionalProperties).

**`zodToJsonSchema(schema, nameOrOptions)`** — name string nests under `definitions` + `$ref`; options: `target`, `$refStrategy`, `definitionPath`, `nameStrategy`, `errorMessages`, `strictUnions`, `override`/`postProcess`.

**Single-tool trick**: one forced tool = one typed output slot; multiple output shapes = multiple tools selected via `tool_choice`. Add `strict: true` for guaranteed schema conformance.

**Why tool use beats regex/free-form**: API-enforced structure (no drift) · type safety via Zod inference · validation *before* business logic (malformed = API/parse error) · schema is version-controlled and reviewable.
