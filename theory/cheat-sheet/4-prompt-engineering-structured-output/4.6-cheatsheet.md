# Domain 4 · Task 4.6 — Design Multi-Instance and Multi-Pass Review Architectures

**Exam objective**: Design review pipelines that separate authorship from review across independent Claude instances and staged passes, and configure extended thinking (`budget_tokens`) / interleaved thinking to add reasoning depth where it pays off.

---

## Key concepts

- **Self-review is structurally unreliable** — asking one instance to review its own output produces *confirmatory*, not *adversarial*, review. "The model is not lazy — it is coherent. Coherence is the problem." Three causes:
  1. **Shared context bias** — reviewer sees all prior reasoning and treats it as justification, not evidence to challenge.
  2. **Conversation-level anchoring** — earlier messages pull on later ones; the writer interprets its own work charitably.
  3. **No independent prior** — a self-reviewer cannot manufacture ignorance of what it just wrote.
- **Architectural fix: separate authorship from review at the API-call level.** Independent reviewers are distinct `messages.create` calls with **no shared conversation history** and no access to the original reasoning context. They receive **only the artifact** (code/doc/plan), not the process that produced it.
- **Domain mental model**: *Independent instances beat self-review. Narrow scope beats omnibus review. Findings beat re-reading.*
- **Extended thinking** — manual mode where you set a fixed thinking token budget per request via `thinking: {type: "enabled", budget_tokens: N}`. Claude reasons against the budget before its final answer. Gives predictable latency and precise cost control.

---

## Patterns & when to use them

### Multi-instance (independent, parallel) review
Distinct API calls, clean `messages` arrays, run concurrently on the same artifact. Use for verification: independent instances have no anchoring bias, so they surface issues a self-review would rationalize away. This is the core "multiple independent instances for verification" pattern.

### Split-role reviewers (specialization by system prompt)
Assign **distinct roles to distinct instances**, each with an exclusive scope in its system prompt (and explicit instructions to ignore other categories). Three roles cover most cases:
- **Security reviewer** — injection (SQL/XSS), auth bypass, hardcoded secrets, unsafe deserialization.
- **Performance reviewer** — N+1 queries, unbounded loops, sync I/O on hot path, missing memoization / unnecessary re-renders.
- **Correctness reviewer** — logic errors, unhandled edge cases, off-by-one, bad null/undefined assumptions, missing error propagation.

Run in parallel on the same file; findings are **structurally tagged by role** so aggregation can route (e.g. critical security findings → security team). Improves precision, cuts false positives from mixed concerns.

### Multi-pass (staged pipeline) — for large codebases / complex outputs
1. **Per-file analysis pass** — each file reviewed in isolation by a dedicated instance; narrow scope; findings structured & stored.
2. **Cross-file integration pass** — instances receive file pairs/clusters **plus prior per-file findings**; find issues visible only across components: interface mismatches, inconsistent error-handling conventions, shared-state mutations.
3. **Final synthesis pass** — a single aggregating instance takes **all findings only** (never re-reads source), deduplicates, assigns priorities, produces an actionable summary.

Benefits: keeps context windows small, parallelizes naturally, and ensures no single instance both generates *and* validates a conclusion.

### When extended thinking helps
- Complex reasoning tasks (hard math/logic, multi-step analysis) — larger budget enables more thorough analysis, with **diminishing returns**.
- When you need **predictable latency** or **precise control over thinking cost** → manual mode.
- Interleaved thinking → when Claude must reason **between tool calls** within one assistant turn.
- Not worth it for simple tasks — start near the 1,024 minimum; adaptive mode may skip thinking entirely on easy inputs.

## Gotchas / exam traps

**Review-architecture mistakes (all five from the objective):**
1. **Passing original conversation history to the reviewer** — reviewer inherits the same anchoring bias as self-review. Always start review calls with a **clean `messages` array**.
2. **Running per-file and cross-file passes in the same instance** — one big-context review of many files degrades per-file attention; keep passes separate.
3. **Skipping the synthesis pass / acting on raw findings** — parallel instances produce duplicates and conflicting severities; without aggregation, pipelines double-count and over-alert.
4. **Giving all roles the same system prompt** — each instance then tries to cover everything → redundant overlap, defeats role isolation. Each role needs an **exclusive** scope + explicit "ignore other categories."
5. **Using the synthesis instance to re-read source files** — inflates tokens and lets a less-focused general impression override specialist findings. Synthesis works on **findings only**.

**Extended-thinking traps:**
- `budget_tokens` **minimum is 1,024** — API rejects smaller values.
- `budget_tokens` is a **target, not a hard cap**; `max_tokens` is the true ceiling on total output. Thinking tokens count toward `max_tokens` (so budget must leave room for the answer) — **except** interleaved thinking, where the budget spans all thinking blocks in a turn and `budget_tokens` **can exceed** `max_tokens`.
- **No cache pre-warming**: because `budget_tokens` < `max_tokens`, you can't combine extended thinking with `max_tokens: 0`.
- **Changing `budget_tokens` invalidates prompt cache** (the budget is rendered into the prompt) — pick a budget and hold it stable for a cached conversation.
- **Budgets > 32k** → use **batch processing** (long requests hit timeouts / open-connection limits).
- Manual mode requires the **final assistant turn to begin with a thinking block** (adaptive drops this).
- **Deprecation direction**: `thinking:{type:"enabled"}`+`budget_tokens` is deprecated on 4.6 models (still works), **rejected with 400 on 4.7+**. Where both exist, prefer **adaptive thinking**. Migration: remove `budget_tokens`, set `thinking:{type:"adaptive"}`, control depth with `output_config:{effort:...}`.

## Quick reference

**Manual extended thinking (Messages API):**
```python
response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=16000,
    thinking={"type": "enabled", "budget_tokens": 10000},
    messages=[...],
)
# response.content has "thinking" blocks + "text" blocks
```
- `thinking.type = "enabled"` + `budget_tokens` (min 1,024).
- Simple tasks: start ~1,024, increase. Complex: start 16,000+.
- Track real cost via `usage.output_tokens_details.thinking_tokens` (on final `message_delta` when streaming).
- On Opus 4.5 (effort-supporting, thinking-only): set **both** `effort` (shapes response) and `budget_tokens` (thinking depth).

**Interleaved thinking (reason between tool calls, one turn):**
- Enable in manual mode with beta header `interleaved-thinking-2025-05-14` (Opus 4.5 / Sonnet 4.5 / earlier Claude 4).
- 4.6 split: Sonnet 4.6 header still works but deprecated; **Opus 4.6 manual has no interleaved thinking** — use `thinking:{type:"adaptive"}`.
- Haiku 4.5 doesn't support it. Only for tools via the Messages API. Adaptive interleaves automatically (no header).

**Migrate to adaptive:**
```json
// manual (deprecated 4.6, rejected 4.7+)      // adaptive
{"thinking":{"type":"enabled",                 {"thinking":{"type":"adaptive"},
             "budget_tokens":10000}}            "output_config":{"effort":"high"}}
```
Behavioral change: fixed budget → thinks every request; adaptive → decides per request, may skip on easy inputs.

**Multi-pass review pipeline:**
```
per-file pass  →  cross-file integration pass  →  final synthesis pass
(isolated,        (file pairs + prior             (findings only, dedupe,
 per role,         findings; interface/            prioritize; never
 parallel)         shared-state issues)            re-reads source)
```

**Multiple independent instances for verification:** N distinct `messages.create` calls, clean history, parallel (`Promise.all`), findings tagged by role → aggregated. Independence is what makes the verification trustworthy.
