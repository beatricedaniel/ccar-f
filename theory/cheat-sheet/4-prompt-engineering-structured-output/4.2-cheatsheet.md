# Domain 4 · Task 4.2 — Apply Few-Shot Prompting to Improve Output Consistency

**Exam objective:** Embed concrete input→output examples in the prompt to make Claude's format, style, and edge-case handling consistent — because *examples beat instructions*.

## Key concepts
- **Few-shot (a.k.a. multishot) prompting** = embedding concrete input→output examples directly in the prompt. You *demonstrate* rather than *describe*; the model generalizes to new inputs in the same style/format/register.
- **The single most reliable lever for output consistency.** Instructions are ambiguous ("return a concise summary" varies by reader); an example shows exactly how long, what voice, what structure.
- **Why examples beat instructions:** instructions describe a rule; examples instantiate it. "Return JSON with `status` and `message`" still leaves casing/nesting/extra-field/null variance. One example removes most; 2–3 remove almost all.
- **The model learns locally** — it pattern-matches examples in the context window, NOT a memorized rulebook. So a few well-chosen examples can *override* the model's general tendencies / common conventions.
- **Targeting ambiguous cases:** generic examples teach the happy path; targeted examples teach the edge cases you care about. String-or-array input → show one of each. Optional field → show omitted AND null. Classification boundary → include an example at the boundary. *A single well-targeted tricky example beats three easy ones.*
- **Anthropic docs "make examples":** Relevant (mirror your real use case), Diverse (cover edge cases, vary enough that Claude doesn't pick up unintended patterns), Structured (wrap in `<example>` tags; multiple in `<examples>` tags so Claude distinguishes them from instructions). Docs recommend **3–5 examples** for best results; you can ask Claude to evaluate examples for relevance/diversity or generate more.
- **Multishot examples work WITH thinking:** put `<thinking>` tags inside your few-shot examples to demonstrate the reasoning pattern — Claude generalizes that style to its own thinking blocks.

## Patterns & when to use them — how many examples
| # examples | When |
|---|---|
| **1** | Establishes format; simple schemas |
| **2–3** | **The practical default** — happy path + ≥1 variation |
| **4–5** | Complex output space, many edge cases, high format sensitivity (docs: 3–5) |
| **>5** | Rarely necessary; increases token cost without benefit |

- **Stop adding examples** once the model produces correct output on your test inputs. Beyond diminishing returns = more cost, no gain.
- **Placement:** put few-shot examples at the **END of the system prompt**, immediately before the first human turn (maximize recency / influence on first output). Examples buried in the first third of a long prompt get partially overridden by later instructions.
- **Wrap long examples in delimiters** (XML tags reliable) so the model separates examples from directives.
- **Zero-shot vs few-shot:** zero-shot (instructions only) for simple/well-conventioned formats; few-shot when format deviates from convention, edge cases matter, or consistency is critical.
- **Few-shot + native structured output:** few-shot *improves* consistency; a machine-validated schema (tool use / structured outputs) *enforces* it. Combine both for high-stakes integrations.

## Gotchas / exam traps
- **Only happy-path examples** = no guidance for messy real-world data. Write examples for the cases most likely to go wrong.
- **Describing format in prose AND in examples** = redundancy → potential contradiction if they diverge. Let examples carry the format; use prose ONLY for what can't be shown (e.g. "never include PII in the rationale field").
- **Examples placed too early** in a long system prompt get overridden — move to the bottom.
- **Inconsistent example structure** (one uses `"label"`, another `"classification"`) teaches nothing stable. Every example must use the EXACT same schema, field names, and value formats.
- **Adding more examples when the real problem is a bad schema** — if output is inconsistent despite several examples, the format itself is under-constrained. Define a strict schema (JSON Schema / TypeScript type), don't pile on examples.
- **Relying on few-shot alone for high-stakes structured output** — pair with tool-use / structured output for enforcement.
- Distractor: "more examples always = more consistency." False — diminishing returns; wrong schema is the usual culprit.

## Quick reference
- **Mental model:** *Specificity beats vagueness. **Examples beat instructions**. Schemas beat parsing.*
- **Example structure tags:** single `<example>`; multiple wrapped in `<examples>`.
- **Example quality triad:** Relevant · Diverse · Structured.
- **Sweet spot:** 2–3 targeted examples (docs say 3–5); place at end of system prompt.
- **Sample pattern (classification):** happy path + ambiguous boundary + targeted edge case (e.g. sarcasm → NEGATIVE), each `Input:`/`Output:` with identical JSON schema, no prose format description.
