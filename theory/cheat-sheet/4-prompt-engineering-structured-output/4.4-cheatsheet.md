# Domain 4 · Task 4.4 — Implement Validation, Retry, and Feedback Loops

**Exam objective**: Treat model output as an *unverified claim* — validate it against a schema, and on failure retry with a prompt that includes the precise validation error; bound the loop, detect non-convergence, and reduce hallucinations via uncertainty, grounding, and citations.

## Key concepts

- **Model output = unverified claim.** Never trust a single call. Validate at the boundary *before* the result touches downstream code.
- **Mental model: agent = compiler, Claude = source file.** A compiler doesn't ask you to rewrite the whole file for one type error — it reports the exact error + location. **The retry prompt is your error report.**
- **Validation-Retry loop (5 steps):**
  1. Call Claude with the task prompt.
  2. Parse + validate output against schema/assertions.
  3. Valid → accept and proceed.
  4. Invalid → build retry prompt containing **(a) original task, (b) the invalid output, (c) a precise description of the validation failure**.
  5. Repeat.
- **Naive retry vs retry-with-error-feedback** — the whole distinction is **step 4**. Re-sending the same prompt with no error context is a coin flip; Claude has no new info and often reproduces the same bad output.
- **Schema is the contract.** Define it *before* writing the prompt; the prompt should reference it explicitly. Schemas do two jobs: (1) make validation errors machine-readable, (2) force you to specify output shape up front (not reverse-engineered).
- **`maxAttempts` (hard bound).** Unbounded retries = self-inflicted DoS (token/rate-limit exhaustion). Beyond budget, **fail explicitly** — never silently degrade.
- **Diminishing returns after ~3 attempts.** If Claude can't produce valid output in 3 tries with progressively more specific feedback, the root cause is usually: schema too strict / contradicts task, prompt ambiguous (same class of error), or output format beyond model capability for that input. Surface to caller — don't just raise `maxAttempts`.
- **`detected_pattern` tracking.** Accumulate error *type/category* counts across attempts (`Record<string, number>`). When the same error category recurs (≥2), the loop isn't converging → stop and escalate/adjust (broaden schema, simplify prompt, route to fallback). Catches the subtle failure where each attempt fails *differently* and silently burns the budget.

## Patterns & when to use them

| Pattern | Use when |
|---|---|
| **Validate → retry → feedback loop** | Any structured/JSON output that downstream code depends on. Core pattern. |
| **Re-prompt with validation errors** | Always on retry — include invalid output + specific error string. This is what makes retry converge instead of coin-flip. |
| **`detected_pattern` loop detection** | Long/expensive loops; detect non-convergence early (same error twice → throw). |
| **Distinguish failure classes** | Missing optional field ≠ malformed date. Log error types distinctly so corrections stay focused. |
| **Escalate / fallback** | After max attempts or detected non-convergence — surface a descriptive error, don't retry forever. |

**Hallucination reduction (grounding output in truth):**

*Basic strategies*
- **Allow "I don't know."** Explicitly give Claude permission to admit uncertainty — simple, drastically cuts false info.
- **Direct quotes for grounding.** For long docs (**>20k tokens**), have Claude extract word-for-word quotes *first*, then perform the task on them.
- **Verify with citations.** Cite quotes/sources per claim → auditable. Have Claude find a supporting quote *after* answering; **if no quote, retract the claim.**

*Advanced techniques*
- **Chain-of-thought verification** — reason step-by-step before final answer (reveals faulty logic).
- **Best-of-N verification** — run same prompt N times, compare; inconsistency signals hallucination.
- **Iterative refinement** — feed outputs back as inputs, ask Claude to verify/expand.
- **External knowledge restriction** — instruct Claude to use *only* provided documents, not general knowledge.

## Gotchas / exam traps

1. **Retrying without error feedback** — THE most common mistake. Same prompt = same output.
2. **No `maxAttempts` limit** — unbounded loop exhausts tokens / hits rate limits.
3. **Schema defined after implementation** — schema reverse-engineered from outputs. Define schema *first*; it's the contract.
4. **Treating all validation failures as equal** — conflating distinct failures (missing field vs bad date) → unfocused corrections. Log types distinctly.
5. **Ignoring diminishing returns** — 3 failures with specific feedback and no improvement means the *strategy* is wrong. Audit schema/prompt before raising `maxAttempts`.
6. **Not tracking patterns across retries** — without `detected_pattern`, a loop cycling through *different* bad outputs silently burns the budget with no root-cause signal. Track across the *full* sequence, not just the last attempt.
7. **Hallucination techniques reduce but don't eliminate** — always validate critical/high-stakes info independently.

## Quick reference

**Zod validation**
```ts
import { z } from "zod";
const EventSchema = z.object({
  title: z.string().min(1),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/), // YYYY-MM-DD
  location: z.string().optional(),
});
type Event = z.infer<typeof EventSchema>;       // static type from schema
```
- `.parse(input)` → returns validated data or **throws** on failure.
- `.safeParse(input)` → returns `{ success: true, data }` **or** `{ success: false, error }` (no throw — preferred in retry loops).
- Zod: TypeScript-first, zero deps, ~2kb, immutable API, static type inference (`z.infer`), built-in JSON Schema conversion. `npm install zod`; requires TS strict mode.

**Turn Zod issues into a retry-prompt error string**
```ts
const result = EventSchema.safeParse(parsed);
if (result.success) return result.data;
const issues = result.error.issues
  .map((i) => `${i.path.join(".")}: ${i.message}`)   // e.g. "date: Invalid"
  .join("; ");
```

**Retry loop skeleton**
```ts
while (state.attempts < maxAttempts) {
  state.attempts++;
  const feedback = lastError
    ? `\nPrevious output:\n${lastOutput}\nValidation failed: ${lastError}` : "";
  const prompt = TASK + SCHEMA_DESC + rawText + feedback;   // schema referenced explicitly
  const raw = /* claude.messages.create(...) → text */;
  lastOutput = raw;

  let parsed; try { parsed = JSON.parse(raw.trim()); }      // parse JSON defensively first
  catch { lastError = "Not valid JSON"; bump("invalid_json"); if (count>=2) throw; continue; }

  const r = EventSchema.safeParse(parsed);
  if (r.success) return r.data;
  lastError = issuesToString(r.error);
  for (const i of r.error.issues) {                          // fingerprint per field+code
    const key = `${i.path.join(".")}_${i.code}`;
    if (bump(key) >= 2) throw new Error(`Loop detected on ${key} — review schema/prompt`);
  }
}
throw new Error(`Failed after ${maxAttempts} attempts. Last error: ${lastError}`);
```

**Order of operations:** parse JSON (try/catch) → `safeParse` schema → on fail, build error string + bump `detected_pattern` → feed error back → stop at `maxAttempts` or on repeated error type.

**Hallucination cheat-list:** allow "I don't know" · quote-first grounding (>20k tokens) · cite + retract-if-no-quote · CoT verification · best-of-N · iterative refinement · restrict to provided docs.
