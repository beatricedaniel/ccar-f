# Domain 4 · Task 4.5 — Design Efficient Batch Processing Strategies

**Exam objective**: Know when and how to use the Message Batches API to process large volumes of requests asynchronously at 50% cost, with correct request tracking (`custom_id`), polling, and per-item failure handling.

## Key concepts

- **Message Batches API** = submit many Messages requests in one call; processed **asynchronously**, results retrieved later. Anthropic's first implementation of the batch pattern.
- **50% cost discount**: all batch usage billed at 50% of standard Messages API rates (input *and* output). Discount **stacks with prompt caching**.
- **Processing window**: batches complete "as fast as possible" — most finish in **under 1 hour**; hard ceiling is **24 hours**. Access results when all requests complete OR after 24h, whichever comes first. Requests not processed within 24h → `expired`.
- **Per-item independence**: each request processed independently; one failure does NOT cancel the batch. There is **no aggregate failure signal** — you must inspect each result.
- **`custom_id`**: caller-assigned ID (1–64 chars, `^[a-zA-Z0-9_-]{1,64}$`) required on every request; preserved in results so you can map result → source. Scoped to a single batch.
- **Results order is NOT guaranteed** — always match by `custom_id`, never by position.

## Patterns & when to use them

**Use Message Batches (async) when:**
- Non-interactive / offline workloads: document summarization pipelines, bulk sentiment analysis, dataset annotation, offline evals, content moderation, bulk content generation.
- No human/process is waiting in real time; results feed a downstream pipeline that runs later.
- You want to optimize cost (50% off) and throughput over latency.

**Use standard Messages API (real-time) when:**
- Interactive workloads: chat UIs, tool-calling agents acting on each response, streaming UI updates — anything latency-sensitive.

**Decision rule**: *If a human or dependent process is waiting for the response in real time → Messages API. If results feed a pipeline hours later → Batches.*

**Cost tradeoff**: Batches = half price + higher throughput, paid for with up-to-24h latency. Not a latency optimization — it's a cost/throughput optimization.

**Recommended architecture — job-queue model**: submit batch → **persist `batch_id` to durable store** → process results in a separate scheduled task. Treat completion as an *event*, not a blocking call.

**Prompt caching + batches**: include identical `cache_control` blocks in every request, keep a steady request stream (cache entries expire after 5 min), maximize shared cached content. Cache hits are best-effort (typical 30%–98%). Consider the **1-hour cache duration** for batches with shared context.

## Gotchas / exam traps

- **Never use batches for interactive/UI-waiting workloads** — breaks UX.
- **Always branch on `result.result.type`** before reading the message payload. Assuming all succeeded = silent data loss.
- **No tight polling loops**. Poll every ~60s (or every 5 min for large jobs); tight loops waste quota and gain nothing.
- **Don't reuse `custom_id` across batches** without encoding a batch/record ID — `custom_id` is scoped per batch.
- **Don't assume instant completion** — code expecting results in seconds produces false timeouts.
- **Persist `batch_id`** before proceeding — crash after submit = results unretrievable otherwise.
- **`max_tokens` must be ≥ 1**; `max_tokens: 0` (cache pre-warming) is NOT supported in a batch.
- Unsupported params (return validation error): `stream: true`, `speed`/Fast mode, `store`/`previous_thread_event_id` (Threads), `cache_hint`/`context_hint`, `max_tokens: 0`. Validation of `params` is async → validation errors surface only after processing ends. Dry-run one request shape against Messages API first.
- **You are NOT billed** for `errored`, `canceled`, or `expired` requests.
- Batches are **Workspace-scoped**; over 256 MB → `413 request_too_large`.

## Quick reference

| Item | Value |
|---|---|
| Cost | **50%** of standard Messages API rates (input & output); stacks with caching |
| Max requests / batch | **100,000** Message requests |
| Max size / batch | **256 MB** (whichever limit hit first) |
| Processing window | Most < **1 hour**; hard max **24 hours** → unprocessed = `expired` |
| Results availability | **29 days** after batch creation (then batch viewable but results not downloadable) |
| `custom_id` | Required, unique, **1–64 chars**, `^[a-zA-Z0-9_-]{1,64}$`; used to match results |
| Supported models | All active models |
| `max_tokens` | Must be ≥ 1 (standard cap 128k; beta `output-300k-2026-03-24` raises to 300k) |

**Lifecycle**: 1) **Create** (`POST` requests, up to 100k) → receive `batch_id` (`msgbatch_…`). 2) **Poll** status until done. 3) **Retrieve results** (stream). 4) **Handle failures** — separate succeeded/errored, retry errored in a new batch.

**`processing_status`**: `in_progress` → `ended` (all done) → also `canceling` after a cancel request (settles to `ended`). Poll until `ended`.

**`request_counts`** object: `processing`, `succeeded`, `errored`, `canceled`, `expired`.

**Four result types** (per item):
- `succeeded` — includes the message result.
- `errored` — request failed (invalid request or internal error); check `result.error.error.type` (e.g. `invalid_request_error` = fix body before retry; else server error = retriable). Not billed.
- `canceled` — user canceled before send. Not billed.
- `expired` — hit 24h before send. Not billed.

**Results retrieval**: available at the batch's `results_url`; format is **`.jsonl`** (one JSON object per line, newline-delimited). **Stream** results (don't download all at once). Order not guaranteed → match by `custom_id`.

**SDK surface**: `client.messages.batches.create` / `.retrieve` / `.results` / `.list(limit=…)` / `.cancel`. Delete after processing: `DELETE /v1/messages/batches/{batch_id}` (cancel first if in progress). Data retained up to 29 days.
