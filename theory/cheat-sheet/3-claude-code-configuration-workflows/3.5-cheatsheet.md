# Domain 3 · Task 3.5 — Apply Iterative Refinement Techniques for Progressive Improvement

**Exam objective**: Treat Claude as a collaborator in a feedback loop — converge on high-quality output through targeted, multi-turn refinement (progressive drafts, example/test anchors, TDD-style correction) instead of demanding perfection in one prompt.

## Key concepts

- **Iterative refinement**: each exchange narrows the gap between what you got and what you need. The *feedback/measurement* is more valuable than the initial output.
- **Domain mental model — gradient descent**: start at a rough approximation → measure distance from target → adjust → repeat. Convergence, not one-shot correctness.
- **Converge together, not "get it right once"**: reframes the interaction around a concrete artifact you can react to, avoiding the blank-page problem.
- **Claude retains conversation context**: refine by *reference* ("the previous version"), not by restating the full spec each turn.
- **RED / GREEN / REFACTOR (TDD cycle)** maps directly onto multi-turn prompt refinement — this mapping is the headline exam takeaway.

## Patterns & when to use them

| # | Technique | What you do | Use when |
|---|-----------|-------------|----------|
| 1 | **Progressive improvement** | Ask for a "rough first pass, we'll refine it" | Blank page; want a concrete artifact to react to; reduces over-hedging/over-explaining |
| 2 | **Input/output examples as anchor** | Give concrete `input → output` pairs as the spec (like a unit-test suite) | Behavior is ambiguous; each example (esp. edge cases) rules out a class of wrong implementations |
| 3 | **Test-driven iteration (TDD)** | Provide failing tests in the prompt; ask for an implementation that satisfies them | You have (or can write) tests; want objective pass/fail criteria |
| 4 | **Interview pattern** | Instruct Claude to list ambiguities / ask clarifying questions *before* coding | Underspecified tasks, non-obvious constraints (perf budgets, data shape, side effects). One clarify round often *halves* revision cycles |
| 5 | **Structured feedback loops** | Name exactly what was wrong + the desired change | Every iteration — precise feedback ("creates a new array each call → reuse the buffer") gives targeted fixes; vague feedback → vague results |

### TDD loop with Claude Code (RED → GREEN → REFACTOR)
1. **RED** — provide failing test cases as part of the prompt.
2. **GREEN** — ask Claude for the implementation that satisfies them.
3. **REFACTOR / IMPROVE** — review, request refactoring if needed.
- On failure: **feed the exact failure back verbatim** (assertion + received value). Claude reasons about the precise mismatch without restating full context.

### Worked 3-round example (normalizeUser)
- **R1 Interview** — "list any ambiguities before implementing" (trim? null vs omit? lowercase email? unknown fields?) → user answers → implement with full context.
- **R2 Examples-as-spec** — give input/output pairs showing trim + lowercase + strip-unknown behavior.
- **R3 Test-driven correction** — paste the one failing test verbatim, ask for the localized fix.
- Result: three *focused* rounds, never restarting from scratch.

## Gotchas / exam traps

1. **Demanding perfection in the first prompt** — loading every edge case at once → bloated, defensive output. Lead with the core case; *layer edge cases in during refinement*.
2. **Vague feedback** ("make it better", "this isn't quite right") → vague improvement. Always state: what it did / what you expected / the difference.
3. **Restating full context every iteration** — wastes context and introduces inconsistencies. Refer back by reference; Claude remembers.
4. **Skipping the interview pattern on ambiguous tasks** — guarantees rework; one clarify exchange beats 2–3 revision cycles.
5. **Rewriting from scratch on the first test failure** — a single failure is usually a *localized* defect. Feed the failure back; targeted correction preserves working parts.
6. **Forgetting to close the loop** — after a fix, re-verify against **all** prior examples/tests, not just the one that failed (avoid regressions).

## Quick reference

**Refinement loop**: rough draft → measure gap → precise feedback → targeted correction → re-verify against everything → repeat until converged.

**Verification-driven iteration**: examples and tests are *objective anchors*. Examples ≈ unit-test suite; each rules out wrong implementations. Feedback > output.

**TDD workflow (test-first with Claude Code)**:
```
RED     → give failing tests in the prompt
GREEN   → ask for implementation that passes them
REFACTOR→ review + request cleanup
FAIL?   → paste exact failure verbatim → localized fix → re-run ALL tests
```

**Framings to memorize**:
- Progressive: *"Give me a rough first pass at this function. We'll refine it."*
- Interview: *"Before implementing, identify any ambiguities and ask me to resolve them. Only proceed once you have enough information."*
- Structured feedback: *"The previous version creates a new array on every call. Refactor to reuse the existing buffer."*
