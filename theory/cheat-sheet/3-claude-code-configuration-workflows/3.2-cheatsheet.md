# Domain 3 · Task 3.2 — Create and Configure Custom Slash Commands and Skills

**Exam objective**: Build project- and user-scoped custom slash commands (Markdown + YAML frontmatter + `$ARGUMENTS`) and reusable Skills (`SKILL.md` knowledge packages), knowing where each lives, which frontmatter fields control execution/permissions, and when to reach for a command vs. a skill.

> Note on sources: the **Connectry handout** (official objective) and the **Claude Code docs** (reference) differ on a few file paths. Commands and skills have *merged* in current Claude Code — a file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy`. The exam question bank tends to follow the handout's framing; where they diverge it is flagged below.

---

## Key concepts

- **Custom slash command** = a Markdown file that is a *prompt template*. Says "do X with `$ARGUMENTS`". Invoked by its file/dir name after `/`.
- **Skill** = a `SKILL.md` file that is primarily a *structured knowledge document* ("here is everything about domain Y — now apply it"). Loaded on demand; body loads **only when used**, so long reference material costs almost nothing until invoked. Claude can auto-load a skill when relevant, or you invoke it with `/skill-name`.
- **Commands and skills merged**: same invocation mechanism. If a skill and a command share a name, **the skill takes precedence** (`.claude/commands/deploy.md` + `.claude/skills/deploy/SKILL.md` → `/deploy` runs the skill).
- **Progressive disclosure**: only `SKILL.md` (and each skill's short `description`) is always available; the full body + supporting files load on demand. Keep `SKILL.md` under ~500 lines and move detail into sibling files (`reference.md`, `examples.md`, `scripts/`) referenced from `SKILL.md`.
- **Frontmatter** = fenced YAML block at the top of the file between `---` markers, controlling execution behavior, permissions, and invocation.

## Patterns & when to use them

### Slash command vs. Skill

| | Custom slash command | Skill |
|---|---|---|
| Primary payload | Imperative prompt ("do X") | Knowledge doc / conventions / multi-step procedure |
| File | `.claude/commands/<name>.md` | `.claude/skills/<name>/SKILL.md` (a directory) |
| Supporting files | No | Yes — bundle `scripts/`, `reference.md`, etc. |
| Auto-invoked by Claude | Only when you type it | Yes, when `description` matches (unless disabled) |
| Best for | Repeatable actions: run tests, generate release notes, commit-message template | Team conventions, domain ontologies, architectural patterns, style guides |

Docs recommend **skills** over plain command files because skills add supporting files, richer frontmatter, and auto-loading. (Command files ignore the `name` and `paths` frontmatter fields; everything else works the same.)

### Project vs. User scope

- **Project scope** — `.claude/commands/` or `.claude/skills/` at repo root. Shared with every contributor. Use for codebase-coupled workflows (test suite, review checklist, release notes). *Must be exactly `<projectroot>/.claude/commands/<name>.md`* — a nested subdir won't be discovered (except the skills sub-namespacing rules below).
- **User (personal) scope** — `~/.claude/commands/` or `~/.claude/skills/`. Travels with you across all projects. Use for personal patterns (commit template, debug scaffold, refactor sequence).
- **Precedence** — Handout: project overrides user (team can override personal defaults). Full docs skill precedence: **enterprise > personal > project**, and any local skill/command overrides a claude.ai-synced skill of the same name.

### Arguments

- `$ARGUMENTS` — the full argument string as typed. `/fix-issue 123` → `Fix GitHub issue 123 ...`.
- `$1`, `$2`, ... / `$ARGUMENTS[0]`, `$ARGUMENTS[1]` — positional (0-based for the `[N]` form; `$1` = first, `$2` = second). `$N` is shorthand for `$ARGUMENTS[N]`.
- `$name` — named argument declared in `arguments:` frontmatter list (`arguments: [issue, branch]` → `$issue` = first, `$branch` = second).
- If a command/skill takes args but no placeholder consumes them, Claude Code appends `ARGUMENTS: <value>` so Claude still sees them.
- Indexed placeholder with no matching arg stays as literal text; named placeholder with no arg expands to empty string.

### When to use a forked context

- `context: fork` — runs the command/skill in an **isolated sub-agent**. Gets a copy of conversation state, writes nothing back to the parent. Use for token-heavy, speculative, or noisy work (deep security audit, large refactor preview). The skill body becomes the subagent's prompt; it has no access to your conversation history. Pair with `agent:` to pick the subagent type (`Explore`, `Plan`, `general-purpose`, or a custom `.claude/agents/` agent).

## Gotchas / exam traps

- **Wrong directory** — a command file must be exactly at `<projectroot>/.claude/commands/<name>.md`. Nested-in-a-random-subdir files are not discovered.
- **Omitting `context: fork` for expensive commands** — long/exploratory runs then eat the parent context window and pollute the conversation.
- **Over-permissive `allowed-tools`** — leaving it *unset* silently grants **all** tools (write + execute), even on a read-only doc command. Always declare the minimal set (`allowed-tools: [Read]`).
- **`argument-hint` is UI-only** — a palette placeholder label. It does **not** validate or enforce argument format/presence. Validate in the prompt body if the arg is required.
- **Treating a skill like a command** — skills are knowledge payloads. A skill ending in "now do X" behaves like a command and can cause side effects when invoked without a clear target. Keep skills descriptive; let the calling context supply the action. To make a task-style skill safe, set `disable-model-invocation: true` so only the user can trigger it.
- **`disable-model-invocation: true` vs `user-invocable: false`** — opposite controls: the first hides the skill from *Claude* (you can still `/name` it, description leaves context); the second hides it from *you/the `/` menu* (only Claude auto-invokes it). Default for both booleans is the permissive side.
- **Skill vs command name clash** → the **skill wins**.
- **Malformed frontmatter YAML** → skill loads with empty metadata: `/skill-name` still works but there's no `description` for Claude to auto-match on. Run with `--debug` to see the parse error; `claude plugin validate <dir>` checks `SKILL.md` files.
- **Body persists across turns** — once a skill loads, its content stays in context every turn (recurring token cost). But an `allowed-tools` grant **clears on your next message** (per-turn only).
- **Injected `!` command output is not re-scanned** — substitution runs once; command output can't emit another placeholder. `!` is only recognized at line start or after whitespace (`KEY=!cmd` is left literal).

## Quick reference

### Locations

| Item | Path | Scope |
|---|---|---|
| Project command | `.claude/commands/<name>.md` | this repo |
| User command | `~/.claude/commands/<name>.md` | all your projects |
| Project skill | `.claude/skills/<name>/SKILL.md` | this project only |
| Personal skill | `~/.claude/skills/<name>/SKILL.md` | all your projects |
| Enterprise skill | managed settings dir `.claude/skills/<name>/` | whole org (highest precedence) |
| Plugin skill | `<plugin>/skills/<name>/SKILL.md` | namespaced `plugin-name:skill-name` |

Command name = file name without `.md`. Skill name = **directory name** (or frontmatter `name:`). Nested `.claude/skills/` in a subdir → skills load when Claude touches a file there, namespaced like `apps/web:deploy`.

### Slash-command / skill frontmatter fields

```yaml
---
name: review                 # (skills only) display/command name; defaults to dir name. Ignored in command files.
description: What it does and WHEN to use it   # recommended — how Claude decides to auto-load
argument-hint: "branch or PR number"           # palette placeholder label only (no validation)
allowed-tools: [Read, Grep]  # least-privilege allowlist; UNSET = all tools. Grant clears next message.
disallowed-tools: [AskUserQuestion]   # remove tools while skill active (can't remove EndConversation)
model: inherit               # model for this skill/turn; same values as /model, or inherit
context: fork                # run in isolated subagent (no writeback to parent)
agent: Explore               # subagent type when context: fork (Explore / Plan / general-purpose / custom)
background: false            # with context: fork, wait for result instead of backgrounding
disable-model-invocation: true   # only USER can invoke (/name); hides from Claude auto-load
user-invocable: false        # only CLAUDE can invoke; hides from / menu (background knowledge)
when_to_use: "extra trigger phrases"   # appended to description (1,536-char cap combined)
paths: "src/**/*.ts"         # glob(s); skill auto-activates only on matching files. Ignored in command files.
hooks: ...                   # hooks registered while skill is active
shell: bash                  # bash (default) or powershell for ! commands
metadata: {...}              # free-form YAML map for your own tooling
---
Prompt / knowledge body here, using $ARGUMENTS, $1, @file, !`cmd` ...
```

- All fields optional; only `description` is **recommended**. Booleans accept `yes/no/on/off/1/0/true/false`.
- Outside Claude Code (claude.ai upload, Skills API, `package_skill.py`) only 6 spec fields are allowed: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Extra keys → hard error. Claude Code-only body features (dynamic `!` injection) don't run on claude.ai/API.

### Dynamic references in the body

- `$ARGUMENTS`, `$1` / `$N`, `$ARGUMENTS[N]`, `$name` — argument substitution (see Arguments above). Escape a literal `$` before a digit/name with `\` (`\$1.00`).
- **`!` `` `cmd` `` — dynamic context injection**: runs a shell command *before* the body reaches Claude and inlines its **output** (not the command). E.g. ``!`git diff HEAD` ``, ``!`gh pr diff` ``. Multi-line: fenced block opened with ` ```! `. A failed injected command **aborts the whole invocation**; append `|| true` for commands expected to exit non-zero (exit 1 from grep/`git diff` is tolerated).
- **`@file`** — file reference (attaches file contents).
- `${CLAUDE_SKILL_DIR}` (skill's own dir), `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SESSION_ID}`, `${CLAUDE_EFFORT}` (low/medium/high/xhigh/max), `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`. Using the same `${CLAUDE_SKILL_DIR}` in both `allowed-tools` and the body lets a bundled script run without a permission prompt (path matches exactly).

### Minimal examples

Project command — `.claude/commands/review.md`:
```markdown
---
context: fork
allowed-tools: [Read, Grep]
argument-hint: "branch or PR number to review"
---
Review all changes in $ARGUMENTS against main. Group findings: CRITICAL, HIGH, MEDIUM, LOW.
```
Invoked: `/review feature/auth-refactor`

Skill — `.claude/skills/deploy/SKILL.md`:
```markdown
---
name: deploy
description: Deploy the application to production
context: fork
disable-model-invocation: true   # side effects → user-only
---
Deploy $ARGUMENTS to production:
1. Run tests  2. Build  3. Push  4. Verify
```

Skill directory (progressive disclosure):
```
my-skill/
├── SKILL.md        (required — overview + navigation, <500 lines)
├── reference.md    (loaded only when needed)
├── examples.md     (loaded only when needed)
└── scripts/helper.py  (executed, not loaded into context)
```

### Managing / disabling

- Disable ALL skills: deny the `Skill` tool in `/permissions`. Allow/deny specific: `Skill(deploy)` exact, `Skill(deploy *)` prefix.
- `skillOverrides` in `.claude/settings.local.json` (or via `/skills` menu, Space to cycle): per-skill state `"on"` / `"name-only"` / `"user-invocable-only"` / `"off"`.
- Turn off bundled skills: `disableBundledSkills` (keeps `/doctor`).
