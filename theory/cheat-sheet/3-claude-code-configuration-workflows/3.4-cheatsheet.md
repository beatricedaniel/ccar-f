# Domain 3 · Task 3.4 — Determine When to Use Plan Mode vs Direct Execution

**Exam objective**: Judge whether a task calls for Plan Mode (think-first, read-only investigation → written plan → approval → execute) or Direct Execution (apply changes immediately), based on scope, risk, familiarity, and reversibility — and know that using the wrong mode has real costs in *both* directions.

## Key concepts

- **Two execution modes.** Claude Code offers **Plan Mode** and **Direct Execution**. Choosing is a judgment call balancing **thoroughness vs. speed**. Wrong mode either way is costly:
  - Over-plan a simple task → friction/waste, no risk reduction.
  - Under-plan a complex change → cascading mistakes, half-broken builds that are hard to recover from.
- **Plan Mode (Shift+Tab).** A structured *think-first* workflow. Claude **reads and investigates the codebase without making changes**, produces a **written implementation plan**, and **waits for your approval** before executing. Appropriate when the cost of a wrong move is high.
- **Direct Execution.** Skips planning; **immediately applies changes**. Correct for **narrow, well-understood work** where scope is clear and blast radius is small.
- **Explore subagent = read-only investigation.** Traverses codebase, reads files, builds understanding, modifies nothing. Use as a **precursor to Plan Mode** when you need context before committing to a plan. Runs in its *own context window* and reports a summary back (keeps main context clean).
- **The canonical pattern: Explore → Plan → Execute.** Skipping Explore on unfamiliar code before a large change is a top source of *incomplete plans* (missed call sites, hidden dependencies).

## Patterns & when to use them (the core decision)

**Trigger PLAN MODE when any of these hold:**
- Task touches **3+ files**, especially across different modules/layers.
- **Cross-cutting concerns**: authentication, error handling, logging, DB schema migrations, API contracts.
- **Risk is HIGH**: production systems, shared libraries, public APIs, anything affecting other developers' work.
- You are making an **architectural decision**: choosing a pattern, restructuring a directory, introducing a new abstraction, setting a new convention (error-handling, test pattern, file structure).
- Requirements are **ambiguous** — proceeding without clarification would likely require rework.
- You are in an **unfamiliar codebase** and need to learn the lay of the land first.

**Use DIRECT EXECUTION when:**
- Change is **isolated to a single file** with no downstream effects.
- Task is **mechanical / low-risk**: rename a variable, fix a typo, update a constant, add a comment.
- You **already have a plan** and are executing a specific, pre-defined step.
- **Planning overhead would exceed implementation effort** (a 5-min plan for a 2-line fix is waste).

**Map dependencies BEFORE committing to an approach (run Explore first) when:**
- Mapping **dependency graphs before a refactor**.
- Identifying **all call sites** of a function before changing its signature.
- Understanding **data flow across layers** before modifying a shared model.
- Auditing config / environment-variable usage before adding infrastructure.
- Scope is **unknown** ("how many files call `UserRepository`?") → Explore to find consumers, *then* Plan, *then* Direct Execution per step with review gates.

### Complexity Assessment Rubric

| Factor | Low Complexity → Direct | High Complexity → Plan |
|---|---|---|
| Files affected | 1 | 3+ |
| Cross-cutting concerns | None | Yes (auth, logging, schema) |
| Risk level | Dev/test only | Production / shared API |
| Familiarity with codebase | High | Low |
| Reversibility | Easy (local, no migration) | Hard (DB migration, contract change) |
| Ambiguity in requirements | None | Present |

**No single factor forces a mode — evaluate the aggregate.** A *two-file* change that touches auth schema is still a Plan Mode task.

## Gotchas / exam traps

- **"More files always = Plan Mode" is WRONG.** It's the aggregate. Line count/file count alone doesn't decide it — a small change to a shared interface or a precedent-setting decision warrants Plan Mode regardless of size.
- **Plan Mode is NOT only for large features.** It's equally right for *any precedent-setting decision* (new file structure, new error-handling convention, new test pattern) — architectural decisions are high-leverage regardless of line count.
- **Approving a plan ≠ guarantee of correct execution.** Plan approval gates the *approach*, not the *implementation*. Keep reviewing individual edits after approval.
- **Explore is not optional in code you didn't write.** A plan built on incomplete knowledge misses call sites and hidden dependencies.
- **Most costly single mistake:** directly executing a refactor that touches shared interfaces / cross-cutting concerns *without a plan* — partial changes that break the build mid-way are harder to recover from than a 5-minute upfront plan.
- **Don't over-plan bounded tasks.** Direct Execution is the *right default* for clearly bounded, low-risk edits.
- Explore ≠ Plan. Explore = investigate/understand (read-only, summary out). Plan = produce the approved written implementation plan.

## Quick reference

- **Enter Plan Mode two ways:**
  - Start flag: `claude --permission-mode plan`
  - Mid-session: press **`Shift+Tab`** to cycle permission modes until the status bar shows **`⏸ plan mode on`**.
- **What Plan Mode restricts:** Claude **reads files and proposes a plan but makes NO edits** until you approve — effectively read-only investigation → written plan → approval gate → execute. Status bar reads `plan mode on` while active.
- **Approval / exit:** Claude presents the plan and waits; you approve to proceed (ExitPlanMode — leaving plan mode into execution). You can edit the plan in your text editor before approving.
- **Explore subagent:** `use a subagent to investigate <X>` — reads files in its own context window, reports a summary. Use it to gather context *before* planning; keeps main context clean.
- **Canonical flow for big/unknown work:** Explore (map scope & dependencies) → Plan (define steps, get approval) → Direct Execution per step (with review gates).
- **Decision one-liner:** *Small + isolated + low-risk + familiar + reversible → Direct. Multi-file OR cross-cutting OR high-risk OR architectural OR ambiguous OR unfamiliar → Plan (Explore first if scope unknown).*
