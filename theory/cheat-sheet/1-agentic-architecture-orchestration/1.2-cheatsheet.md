# Domain 1 · Task 1.2 — Orchestrate Multi-Agent Systems with Coordinator-Subagent Patterns

**Exam objective:** Build hub-and-spoke systems where one coordinator decomposes tasks, delegates to isolated specialized subagents, and aggregates their outputs.

## Key concepts
- **Hub-and-spoke (coordinator-subagent) topology:** one coordinator receives a complex task → decomposes into well-scoped subtasks → delegates each to a specialized subagent → aggregates results into the final answer.
- **The coordinator never does everything itself** — it *drives decisions*; each subagent operates within guardrails enforced in code.
- **Guiding mental model: "the model drives decisions, code enforces guardrails."** Claude decides which subagents to invoke and how to interpret outputs; your application code controls which tools each subagent may access and what data it can see.
- **Isolated context (critical principle):** every subagent runs in its own independent conversation. It has NO memory of other subagents and CANNOT read the coordinator's full history. Prevents context contamination, keeps subagents focused.
- **The coordinator is the only node holding the full picture** — single point of synthesis.
- **Task decomposition first:** coordinator's system prompt instructs Claude to analyze the request and produce a structured breakdown of subtasks *before* spawning any subagent. Each subtask = clear scope + defined output format + minimal `allowedTools` list.
- **Result aggregation:** after subagents finish, the coordinator receives their outputs as `tool_result`s, reasons across them, produces the coherent final answer.
- Implementation: each subagent is exposed to the coordinator as a **tool** (e.g. `run_research_agent`); invoking the tool spawns an isolated `messages.create` call with a narrow system prompt and only the needed input.

## Patterns & when to use them
- **Coordinator on a strong model, subagents on cheaper ones:** example uses `claude-opus-4-5` coordinator and `claude-haiku-4-5` subagents. Match model tier to subtask difficulty for cost/latency.
- **Pass only the minimal context each subagent needs** — not the full history.
- **Give each subagent a minimal `allowedTools` list** (or no tools if it only needs to reason).
- **Restrict topology to hub-and-spoke** — route all work through the coordinator; do NOT let subagents spawn other subagents.

## Gotchas / exam traps
- **Common Mistake 1 — Sharing full conversation history with subagents:** bloats context window, leaks unrelated info, produces worse-focused outputs. Give each subagent only its subtask context.
- **Common Mistake 2 — Letting subagents call other subagents directly:** creates uncontrolled fan-out, makes aggregation unpredictable, breaks the single-point-of-synthesis guarantee. Only the coordinator routes work.
- **Common Mistake 3 — Skipping decomposition and going straight to invocation:** leads to overlapping/redundant subagents. Always instruct the coordinator to plan subtasks first — the decomposition is where the model earns its role.
- Distractor: "subagents share memory to coordinate" — WRONG, they are isolated by design.
- The coordinator loop is a normal agentic loop keyed on `stop_reason` (`tool_use` → run subagent tools; `end_turn` → return synthesized text).

## Quick reference

### Coordinator loop shape
1. `messages = [{role: user, content: userTask}]`
2. `while(true)`: call `messages.create` with coordinator system prompt + subagent tools.
3. If `stop_reason == "end_turn"` → return the text block.
4. Else for each `tool_use` block → run the matching isolated subagent, collect `{type:"tool_result", tool_use_id, content}`.
5. Push assistant content + push user message of tool_results; loop.
