# Domain 1 · Task 1.6 — Design Task Decomposition Strategies for Complex Workflows

**Exam objective**: Break complex workflows into subtasks and choose the right decomposition strategy — static (prompt chaining) vs. model-directed (dynamic), parallel vs. shared-context — trading control against flexibility, and picking the correct granularity.

## Key concepts

- **Task decomposition** = breaking work into manageable subtasks. The core decision: *how much control do you retain vs. how much reasoning you delegate to the model.*
- Two fundamentally different strategies: **static sequential (prompt chaining)** vs. **dynamic (model-directed)**. Choosing = trading predictability/auditability against flexibility/adaptivity.
- **Independence invariant**: parallelism is only safe when no subtask reads a sibling subtask's output.
- **Granularity heuristic**: decompose to the level where each subtask can be *clearly specified and independently verified*. If a subtask needs another's output to be validated, merge or explicitly sequence them.
- Modern Claude models handle much multistep reasoning *internally* (adaptive thinking + native subagent orchestration), so explicit chaining is reserved for when you must inspect intermediate outputs or enforce a specific pipeline.

## Patterns & when to use them

### 1. Prompt Chaining — Static Sequential Decomposition
- **What**: Developer hardcodes the subtask sequence in application logic. Each step's output feeds the next step's input. Developer decides the steps, order, and what each receives — upfront.
- **When**: Known, stable structure that does NOT depend on data content, e.g. `extract → transform → validate → write`.
- **Pros**: Predictable & auditable (same path every run); each step unit-testable in isolation.
- **Cons**: Brittle when structure varies by input (3-step pipeline breaks if a 4th step is sometimes needed); context between steps must be explicitly designed — info can be lost at handoff boundaries.
- **Most common chaining pattern = self-correction**: generate draft → Claude reviews against criteria → Claude refines. Each step is a separate API call, so you can log, evaluate, or branch at any point.

### 2. Dynamic Decomposition — Model-Directed Subtasking
- **What**: Give the model a high-level objective; it decides *at runtime* which subtasks to create, in what order, and when the goal is met. The orchestrator loop executes whatever the model requests via tools — no fixed plan.
- **When**: Number/nature of subtasks can't be known in advance, e.g. "refactor this codebase to remove all deprecated API calls" (files, call sites, changes all depend on content).
- **Pros**: Flexible, adaptive to arbitrary inputs.
- **Cons**: Higher token cost (reasons about structure every invocation); harder to test/audit (paths vary per run); needs robust tool design + **loop termination logic** to prevent runaway execution.

### 3. Per-File Analysis — Independent Parallel Processing
- **What**: Each unit (file/chunk) is self-contained: read → analyze → produce result → discard context. Results aggregated after all parallel units finish (`Promise.all`).
- **When**: Linting, summarization, scoring, classification — each item stands alone.
- **Key constraint**: NO subtask may read a sibling's output. Independence is the invariant that makes parallelism safe. Verify independence before parallelizing.

### 4. Cross-File Integration — Shared-Context Processing
- **What**: Tasks needing relationships across files (a type in `types.ts` affects how `handler.ts` is analyzed). Requires shared context: pass all relevant files in one prompt, OR maintain a running synthesis layer that accumulates findings before concluding.
- **When**: Dependency analysis, architectural reviews, refactors that must stay internally consistent — any task where a decision in one file constrains another.
- **Cons**: Context-window pressure grows with file count; **sequential, not parallel** (earlier results needed before later analysis); requires careful summarization to avoid prompt bloat.

### Orchestrator-workers / subagent orchestration (from Agent SDK)
- Modern models **orchestrate subagents natively** — recognize when to delegate to specialized subagents, proactively, without explicit instruction. Just ensure subagent tools are well-defined in tool definitions and let Claude orchestrate.
- **Delegate** to subagents for independent workstreams that don't share state. **Work directly** for simple tasks, sequential operations, single-file edits, or when you must maintain context across steps.
- **Watch for overuse**: newer models (Opus 4.6, Opus 5) over-delegate — may spawn a subagent where a direct grep would suffice. Add explicit guidance on when subagents are/aren't warranted.

### Granularity tradeoffs
- **Finer** (smaller subtasks): more parallelism, less per-step context — but more coordination overhead + more API calls.
- **Coarser**: less overhead — but risks context limits, harder to test/retry individual steps.
- Rule: if two subtasks always run back-to-back with no branching between them, they belong in **one** step.

## Gotchas / exam traps

- **Dynamic decomposition for a fixed workflow** → WRONG. If structure is always the same, a hardcoded chain is cheaper, faster, more testable. Reserve dynamic only for genuinely variable workflows.
- **Parallelizing dependent subtasks** → produces incorrect results. If subtask B needs A's output, `Promise.all` is unsafe. Confirm independence first.
- **Ignoring context-accumulation cost** in cross-file integration → naively appending every file's full content blows the context window. Summarize aggressively between steps.
- **Decomposing too finely** → each extra subtask adds latency, token overhead, and a new failure point. Merge back-to-back non-branching steps.
- **Static ≠ always better**: prompt chaining is brittle when input structure varies. Match the strategy to whether the *workflow shape depends on data content*.
- Don't confuse **prompt chaining (static, developer-controlled sequence)** with **dynamic decomposition (model-controlled at runtime)** — the exam tests which one fits a given scenario.
- Parallel = **independent**; shared-context = **sequential + dependent**. Cross-file work cannot be parallelized.

## Quick reference

| Strategy | Who decides subtasks | When to use | Key risk |
|---|---|---|---|
| **Prompt chaining** (static sequential) | Developer, upfront | Known/stable structure independent of data (extract→transform→validate→write) | Brittle to structural variation; handoff context loss |
| **Dynamic decomposition** (model-directed) | Model, at runtime via tools | Subtask count/nature unknown in advance (codebase-wide refactor) | Token cost; runaway loop; hard to audit |
| **Per-file / parallel** | Independent units | Lint, summarize, score, classify — items stand alone | Breaks if subtasks share state |
| **Cross-file / shared-context** | Sequential w/ accumulation | Dependency/architectural analysis, consistent refactor | Context bloat; can't parallelize |

**Decision flow**: Is workflow shape fixed regardless of input? → **prompt chaining**. Variable/unknown structure? → **dynamic decomposition**. Are subtasks independent? → **parallel (per-file)**. Do subtasks depend on each other? → **sequential shared-context**.

**Self-correction chain** (canonical prompt-chaining example): draft → review against criteria → refine — separate API calls for logging/branching.

**Granularity target**: smallest unit that is clearly specifiable AND independently verifiable; merge non-branching back-to-back steps.
