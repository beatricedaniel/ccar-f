# Domain 1 · Task 1.1 — Design and Implement Agentic Loops for Autonomous Task Execution

**Exam objective:** Build the tool-use loop that drives an agent to completion, using `stop_reason` (not text or iteration caps) as the control mechanism.

## Key concepts
- **Agentic loop cycle:** send message → Claude decides to call a tool → execute tool → return result → Claude decides next step → repeat until done.
- The loop is controlled by the **`stop_reason`** field on every successful Messages API response — it tells you *why* Claude stopped generating.
- Core loop logic: if `stop_reason == "tool_use"` → run tools, append assistant content + `tool_result` (as a user message), loop again. If `stop_reason == "end_turn"` → done, present response.
- Message accumulation: push the assistant's `content`, then push a **user** message whose content is the array of `tool_result` blocks.
- Each `tool_result` block references the originating `tool_use` block via **`tool_use_id`**.
- `stop_reason` is part of the response **body** (a successful 200 response), NOT an error. Errors are separate (HTTP 4xx/5xx).
- The **Tool Runner** (SDK) automates the tool_use loop, result formatting, conversation management, and retries — prefer it over hand-rolling the loop.

## Patterns & when to use them
- **Use `stop_reason` to detect completion** — never parse assistant text (e.g. "I'm done") to decide the loop is finished.
- **Don't use an arbitrary `maxIterations` cap as the primary stop** — it's a safety backstop at most; the real stop is `end_turn`.
- **Truncation handling:** on `max_tokens` or `model_context_window_exceeded`, treat the response as truncated. Either append a "[Response truncated]" notice or continue generating (feed assistant text back + "Please continue from where you left off").
- **Server-tool loops (e.g. web_search):** must handle `pause_turn` — append the assistant response to messages and re-request so Claude can finish. Default server-side sampling limit is **10 iterations** per request.
- **Refusals:** on `refusal`, read `stop_details` for the policy category and retry on a fallback model.
- **`model_context_window_exceeded`:** lets you request max possible tokens without knowing exact input size; response is still valid but capped by context window.

## Gotchas / exam traps
- **`tool_use` vs `pause_turn`:** When Claude stops to call *your* (client) tools, `stop_reason` is **`tool_use`** — you continue by sending client `tool_result` blocks. A response waiting on a client tool **never** has `stop_reason == pause_turn`. `pause_turn` only appears when a **server-tool** sampling loop hits its iteration limit; you continue by sending the response back as-is.
- **Mixed tool calls:** a `tool_use` response can contain a `server_tool_use` (or `mcp_tool_use`) block whose `id` has **no matching result block** — that server tool isn't finished. Detect by checking each server_tool_use `id` for a matching result block. Common when Claude calls a server tool + a client tool in one parallel batch; API returns so you run client tools first.
- **Continuation message rules (server tools):** the follow-up user message must contain **nothing except** `tool_result` blocks, and the request must keep the same `tools` array. Adding text after the tool_result blocks ends the turn / causes a 400. Dropping the waiting server tool from `tools` → 400 ending in "...but no `web_search` tool was provided".
- Missing a `tool_result`, or placing one after other content → error: "tool_use ids were found without tool_result blocks immediately after".
- **`refusal` is a normal HTTP 200**, not an error. Safety classifiers return it in the response body.
- **Streaming:** `stop_reason` is `null` in the initial `message_start`, provided in `message_delta`, and in no other event.
- Empty response text can still be `end_turn` (valid natural completion).

## Quick reference

### `stop_reason` values
| Value | When it occurs | What to do |
|---|---|---|
| `end_turn` | Claude finished naturally (most common) | Use the response |
| `max_tokens` | Hit request's `max_tokens` limit | Raise `max_tokens` or continue |
| `stop_sequence` | Hit a custom stop sequence | Read `stop_sequence` field to see which fired |
| `tool_use` | Claude is calling a (client) tool | Run tool, return `tool_result`, continue loop |
| `pause_turn` | Server-tool sampling loop hit iteration limit (default 10) | Send assistant content back to continue |
| `refusal` | Claude declined to respond | Read `stop_details`, retry on fallback model |
| `model_context_window_exceeded` | Hit model's context window limit | Treat as truncated; response still valid |

### Response fields
- `stop_reason`, `stop_sequence` (which sequence fired, else null), `stop_details` (policy category on refusal, else null), `usage.input_tokens`, `usage.output_tokens`.
- `model_context_window_exceeded` is currently typed only in the SDKs' **`beta`** namespace (`client.beta.messages`). On Sonnet 4.5+ returned without a beta header; older models need `model-context-window-exceeded-2025-08-26` beta header.

### SDK / tool loop essentials
- Roles alternate: assistant content, then user message of `tool_result` blocks.
- Recommended dispatch: branch on `stop_reason` (`tool_use` / `max_tokens` / `model_context_window_exceeded` / `pause_turn` / `refusal` / else=`end_turn`).
- Agent SDK vs alternatives: **Agent SDK** = runs loop in your process (Python/TS library); **Claude Code CLI** = interactive terminal; **Client SDK** = direct API, you implement the loop; **Managed Agents** = hosted REST API, Anthropic runs agent + sandbox.
