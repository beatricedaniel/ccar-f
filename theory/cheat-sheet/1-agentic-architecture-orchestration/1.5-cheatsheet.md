# Domain 1 · Task 1.5 — Apply Agent SDK Hooks for Tool Call Interception and Data Normalization

**Exam objective**: Use the Agent SDK hook system to intercept tool calls at defined lifecycle points (`beforeToolCall` / `afterToolCall`) and enforce **deterministic** validation, transformation, normalization, and redaction in code — rather than relying on probabilistic system-prompt instructions.

---

## Key concepts

- **Hooks = callbacks attached at key points in the agentic loop** without modifying core execution logic. They separate **cross-cutting concerns** (audit logging, sanitization, schema normalization, PII redaction) from **tool implementation**. A tool should not know about these concerns; the hook pipeline handles them once, centrally, consistently — every tool call passes through the same pipeline regardless of which tool.
- **Two central Agent SDK hooks** (the objective's focus):
  - **`beforeToolCall(toolName, toolInput)`** — fires *after* Claude requests a tool but *before* the tool executes. Receives tool name + input args. Use for **input validation and normalization**. Returns the (possibly modified) input object.
  - **`afterToolCall(toolName, rawOutput)`** — fires *after* the tool returns but *before* the result is sent back to the model. Receives tool name + raw output. Use for **output normalization / redaction**. Returns the transformed output the model will see.
- **Deterministic vs. probabilistic compliance** (THE core distinction):
  - **Probabilistic** = putting a rule in the system prompt ("always return dates in ISO 8601") and *hoping* the model follows it. Works most of the time; **fails silently** when it doesn't.
  - **Deterministic** = enforcing the rule in code, in a hook that runs **every time, unconditionally**, before the model ever sees the data. Correct for anything that MUST be reliably true: sanitized inputs, normalized schemas, redacted PII, validated ranges, enforced caps.
- **Interception points map to direction of data flow**: intercept at **before/Pre** for *outbound tool inputs*; intercept at **after/Post** for *inbound tool results*.
- **Normalization examples** (from the reference code):
  - Input: clamp `limit` to a hard cap (`Math.min(limit, 100)`); validate required-field types and throw on mismatch.
  - Output: reformat any `*_at` / `*_date` field to ISO 8601 (`new Date(v).toISOString()`); strip sensitive keys (`password`, `secret`, `api_key`) before they reach model context.
- **Purity discipline**: `beforeToolCall` must **return a new object** (`{ ...toolInput, limit: cap }`), never mutate the argument in place. Hooks should be side-effect-free w.r.t. their inputs.
- **Fail loud**: a validation hook should **throw with a descriptive message**, not catch-and-default. Swallowing errors lets invalid calls proceed undetected.

### Two distinct "hook" systems — do not conflate

| System | Naming | Where defined | Shape |
|---|---|---|---|
| **Agent SDK callback hooks** (this objective) | `beforeToolCall` / `afterToolCall` | In your TypeScript/JS agent code | Functions that receive/return objects |
| **Claude Code hooks** (reference doc) | `PreToolUse` / `PostToolUse` events | JSON settings files / frontmatter | Shell/HTTP/MCP/prompt/agent handlers communicating via stdin + exit codes/JSON |

Both do tool-call interception; the exam may test either vocabulary. The **SDK callback** model is the one named in the objective title.

---

## Patterns & when to use them

- **Use a hook (deterministic), NOT a system-prompt instruction, when** a downstream system depends on the guarantee: schema/format consistency, PII removal, range validation, hard caps. If it "must always be true," it belongs in code.
- **Use a system-prompt instruction (probabilistic) when** the behavior is a soft preference and occasional deviation is acceptable (tone, style, when to reach for a tool).
- **`beforeToolCall` when** you need to reject or reshape *inputs*: type-check required fields, sanitize, enforce caps/whitelists. Throw to halt bad calls early.
- **`afterToolCall` when** you need to normalize or sanitize *outputs*: reformat dates, redact secrets, coerce schema, unwrap non-object results (`{ result: rawOutput }`).
- **Claude Code `PreToolUse` when** you need to *block* a tool call before it runs (e.g. deny `rm -rf`) via `permissionDecision: "deny"` or exit 2.
- **Claude Code `PostToolUse` when** you need to react to / warn about / rewrite a result the tool already produced (`updatedToolOutput`, or exit 2 to surface stderr to Claude even though the tool ran).
- **Prefer static context over a hook** when the info never changes: use `CLAUDE.md` (loads without running a script) instead of a `SessionStart`/`additionalContext` hook.
- **ACI / tool-design principle (Building Effective Agents, Appendix 2)**: invest in tool definitions as much as in prompts. Give the model room to "think," keep formats close to natural text, avoid formatting overhead, use **absolute file paths**, and **poka-yoke** (make args hard to misuse). Hooks complement this by deterministically fixing what the model still gets wrong.

## Gotchas / exam traps

- **System-prompt instruction ≠ guarantee.** "Always return ISO 8601 dates" in the prompt is *probabilistic*; the exam's correct answer for reliability is an `afterToolCall` hook. This is Common Mistake #1.
- **Mutating the input argument** in `beforeToolCall` creates hidden side effects — return a new object instead. (Common Mistake #2.)
- **Swallowing hook errors** (catch → return default) lets invalid calls slip through. Throw explicitly. (Common Mistake #3.)
- **`afterToolCall` runs before the model sees output** — so redaction there actually protects context. Redacting *after* the model already saw it is too late.
- **Direction confusion**: `before/Pre` = inputs; `after/Post` = outputs. Don't swap them.
- **SDK `beforeToolCall`/`afterToolCall` vs Claude Code `PreToolUse`/`PostToolUse`** — different systems, different mechanics. A question naming JSON settings + stdin + exit codes is Claude Code hooks; a question naming callback functions returning objects is SDK hooks.
- **Claude Code exit-code trap**: only **exit 2** blocks through the code alone (for blockable events). Exit 1 (or any non-2) is a *non-blocking error* — the action proceeds. Exit 0 = success/normal. (Exception: `WorktreeCreate` fails on *any* nonzero exit.)
- **`PreToolUse` can block; `PostToolUse` / `PostToolUseFailure` cannot** (the tool already ran) — they only surface stderr/`additionalContext` to Claude.
- **`PermissionRequest` does NOT honor exit 2** — deny via the `decision` object instead.
- **Exit 2 while printing valid JSON still blocks**; even a JSON `permissionDecision: "allow"` cannot override exit 2's block.
- **HTTP hooks can't block via status codes** — must return 2xx with a JSON body carrying the decision fields.
- **`matcher` gotcha**: `mcp__memory` matches *no* tool (exact string); you need `mcp__memory__.*` (the `.*` is required) to match all tools from a server. Bare-string matchers are exact; anything with a regex metacharacter is treated as an unanchored JS regex.
- **Timeout asymmetry**: a timed-out Claude Code *command/http/mcp_tool* `PreToolUse` hook does **not** block (call proceeds via normal permission flow); a timed-out **Agent SDK callback hook** **does** block the tool call.
- **`disableParallel_tool_use`/`tool_choice`**: to *require* a tool call use `tool_choice`, not prompt wording; `{"type":"auto"}` lets Claude decide per turn.
- **`strict: true`** on custom tool definitions guarantees tool calls match your schema exactly — a schema-level guarantee, distinct from runtime hook normalization.

## Quick reference

### Agent SDK callback hooks (objective core)
| Hook | Fires | Receives | Returns / purpose |
|---|---|---|---|
| `beforeToolCall` | after model requests tool, before execution | `toolName`, `toolInput` | validated/normalized **input** object (new object; throw on invalid) |
| `afterToolCall` | after tool returns, before result sent to model | `toolName`, `rawOutput` | normalized/redacted **output** object model will see |

Executor flow: `validatedInput = beforeToolCall(...)` → `rawOutput = await tool(validatedInput)` → `return afterToolCall(toolName, rawOutput)`. Agentic loop wraps each `tool_use` block, pushes a `tool_result` (with `tool_use_id`, `content: JSON.stringify(normalizedOutput)`).

### Claude Code hook events — tool-call cadence (every tool call)
| Event | When | Can block on exit 2? |
|---|---|---|
| `PreToolUse` | before a tool call executes | **Yes** — blocks the call |
| `PostToolUse` | after a tool call succeeds | No (shows stderr to Claude) |
| `PostToolUseFailure` | after a tool call fails | No |
| `PostToolBatch` | after a batch of parallel calls resolves, before next model call | **Yes** — stops loop |
| `PermissionRequest` | tool needs a permission decision | No (use `decision.behavior`) |
| `PermissionDenied` | auto mode denies a call | No (`retry: true` to allow retry) |

Cadences: **per-session** (`SessionStart`, `SessionEnd`) · **per-turn** (`UserPromptSubmit`, `Stop`, `StopFailure`) · **per-tool-call** (`PreToolUse`, `PostToolUse`, …).

### Claude Code hook handler types (`type`)
`command` (shell; stdin in, exit code + stdout JSON out) · `http` (POST JSON to `url`) · `mcp_tool` (call `server`+`tool`) · `prompt` (single-turn model eval) · `agent` (spawn subagent; experimental).

### Exit codes (command hooks)
| Code | Meaning |
|---|---|
| `0` | success; print JSON to stdout for structured control |
| `2` | **blocking error** — blocks the action (event-dependent); stderr = block reason |
| other | non-blocking error — action proceeds |

### JSON output / decision-control fields
- Universal: `continue` (false = stop; takes precedence), `stopReason`, `systemMessage`, `terminalSequence` (OSC 0/1/2/9/99/777 + BEL), `suppressOutput` (no-op).
- `hookSpecificOutput` (needs `hookEventName`): `permissionDecision` (allow/deny/ask/defer) + `permissionDecisionReason` (`PreToolUse`); `updatedInput` (`PreToolUse` rewrite tool args); `updatedToolOutput` (`PostToolUse` rewrite result); `additionalContext` (inject context); `decision.behavior` (`PermissionRequest`); `retry: true` (`PermissionDenied`).
- Top-level `decision: "block"` + `reason` (for `UserPromptSubmit`, `PostToolUse`, `Stop`, etc.). Only value is `"block"`; omit to allow.

### Matcher patterns
- `"*"`, `""`, omitted → match all. Exact-string set: letters/digits/`_`/`-`/space/`,`/`|`. Any other char → unanchored JS regex.
- Tool events match on `tool_name`: e.g. `Bash`, `Edit|Write`, `mcp__memory__.*`.
- MCP tool naming: `mcp__<server>__<tool>` (plugin: `mcp__plugin_<plugin>_<server>__<tool>`).
- `if` field (per-handler, tool events only): permission-rule syntax, e.g. `"Bash(git *)"`, `"Edit(*.ts)"`. One rule only (no `&&`/`||`); fails open when Bash command unparseable.

### Common input fields (Claude Code, on stdin)
`session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode` (`default`/`plan`/`acceptEdits`/`auto`/`dontAsk`/`bypassPermissions`), `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id`; `agent_id` + `agent_type` inside subagents.

### Settings locations & controls
`~/.claude/settings.json` (user) · `.claude/settings.json` (project) · `.claude/settings.local.json` (local, gitignored) · managed policy (org) · plugin `hooks/hooks.json` · skill/subagent frontmatter. Disable: `"disableAllHooks": true`. `once: true` (skill frontmatter only). Path placeholders: `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_ROOT}`. Prefer **exec form** (`args` set) for path placeholders.
