# Domain 1 · Task 1.4 — Implement Multi-Step Workflows with Enforcement and Handoff Patterns

**Exam objective:** Build multi-stage pipelines where each stage's output is programmatically validated (not prompt-trusted) and handed off as a typed payload to the next stage.

## Key concepts
- **Two ways to ensure a workflow progresses correctly:**
  - **Prompt-based guidance** — instructions in the prompt ("always return valid JSON", "only proceed if the previous step succeeded"). Convenient but FRAGILE; provides NO hard guarantees. Model may deviate under long context, unexpected input, or ambiguity.
  - **Programmatic enforcement** — validate outputs in code after each model response before passing to the next stage. If validation fails, halt or retry. The model's intentions are irrelevant.
- **Structured handoff pattern:** each step produces a **typed, validated payload** that the next step receives as input. Don't pass raw text — define an interface/schema for what each stage emits and parse the model's output against it. Creates a clear contract at every boundary.
- **The governing rule:** use **deterministic code** for anything that must be correct (schema validation, precondition checks, **routing logic**); use **model flexibility** for anything requiring judgment (summarization, classification, generation).
- Validation via a schema library (**Zod**): `schema.parse(parsed)` throws `ZodError` if the output doesn't match; wrap in a retry loop (e.g. `maxRetries = 2`) and optionally feed the validation error back into the next attempt.
- **Workflows vs Agents (architectural distinction):** *Workflows* = LLMs + tools orchestrated through **predefined code paths** (predictable, consistent). *Agents* = LLMs **dynamically direct their own processes** and tool usage (flexible, model-driven). Both are "agentic systems."
- Guiding philosophy ("Building Effective Agents"): start simple; add complexity only when it demonstrably improves outcomes. Three core principles: **simplicity**, **transparency** (show planning steps), careful **agent-computer interface (ACI)** design (tool docs + testing).

## Patterns & when to use them (the 5 workflow patterns)
- **Prompt chaining:** decompose into a fixed sequence of steps; each LLM call processes the prior output; add programmatic **gates** between steps. Use when the task cleanly decomposes into fixed subtasks; trades latency for accuracy. (e.g. write marketing copy → translate it.)
- **Routing:** classify input, direct to a specialized follow-up. Use when distinct categories are better handled separately and classification is accurate. (e.g. route support query types; route easy→Haiku, hard→Sonnet for cost.)
- **Parallelization:** run LLM calls simultaneously, aggregate programmatically. Two variants: **Sectioning** (independent subtasks in parallel — e.g. one model answers, another screens for guardrails) and **Voting** (same task run multiple times for diverse outputs / thresholds — e.g. multiple code-vuln reviews).
- **Orchestrator-workers:** a central LLM **dynamically** breaks down tasks, delegates to worker LLMs, synthesizes. Like parallelization but subtasks are NOT pre-defined — the orchestrator decides based on input. Use when you can't predict the subtasks (e.g. multi-file code changes).
- **Evaluator-optimizer:** one LLM generates, another evaluates + gives feedback in a loop until accepted. Use when you have clear eval criteria and iterative refinement adds measurable value (e.g. literary translation).

## Gotchas / exam traps
- **Common Mistake 1 — Trusting the model to self-validate:** "ensure your output is valid JSON" in a prompt is NOT enforcement. Parse and validate in code; if the schema check fails, the step failed regardless of intent.
- **Common Mistake 2 — Passing raw text between stages:** one formatting quirk in stage 1 breaks stage 2. Always parse into a typed structure at each boundary.
- **Common Mistake 3 — Using model output for routing decisions:** letting the model say "PROCEED" mixes concerns. Routing/control flow belongs in deterministic code; drive it off schema-validated fields like `confidence` or `status`.
- Distinguish orchestrator-workers (dynamic subtasks) from parallelization (pre-defined subtasks) — topographically similar, key difference is flexibility.
- Frameworks (Claude Agent SDK, Strands, Rivet, Vellum) can hide the underlying prompts/responses — start with LLM APIs directly; understand what's under the hood.

## Quick reference

### Typed step runner (enforcement) shape
```
runStep(systemPrompt, userMessage, schema, maxRetries=2):
  loop attempts:
    resp = messages.create(...)          # model does the judgment work
    text = join text blocks
    try: parsed = JSON.parse(text); return schema.parse(parsed)   # Zod validation
    catch: retry, else throw after maxRetries
```
- Handoff: `draftStage(research)` receives the *validated* `ResearchOutput`, serialized via `JSON.stringify`.
- Deterministic gate example: `if (research.confidence === "low") throw` — routing decided in code, not by the model.

### Zod essentials (used to define handoff contracts)
- `z.object({...})`, `z.string()`, `z.number().int().positive()`, `z.array(z.string()).min(1)`, `z.enum([...])`.
- `type X = z.infer<typeof Schema>` derives the TS type; `schema.parse()` validates and throws on mismatch.

### Decision cheat: deterministic code vs model
| Must be correct → code | Needs judgment → model |
|---|---|
| Schema/output validation | Summarization |
| Precondition / gate checks | Classification |
| Routing / control flow | Generation / drafting |
