# Domain 1 · Task 1.7 — Manage Session State, Resumption, and Forking

**Exam objective**: Keep a long-running agent coherent across time by persisting session IDs, resuming or forking sessions correctly, and controlling what survives context compaction with authored structured summaries.

---

## Key concepts

- **Session** = a *named, persistent conversation thread* — the full history the SDK accumulates: your prompt, every tool call, every tool result, every response. Written to disk automatically so you can return later. This is what turns a stateless chatbot into a coherent long-running agent.
- **Sessions persist the conversation, NOT the filesystem.** To snapshot/revert file changes an agent made, use **file checkpointing** (separate mechanism). Fork/resume branch the *transcript*, not files — a forked agent's file edits are real and visible to any session in the same directory.
- **Session ID** = a stable reference (a UUID). The **SDK does not maintain a session registry** — *you* persist the ID and pair it with your own metadata (creation time, last-active time, summary version).
- **Three ways to return to a session**: **continue** (most recent, no ID), **resume** (specific ID), **fork** (branched copy).
- **Context compaction**: every context window has a finite token budget. When history approaches the limit, Claude Code **summarizes older turns into a compressed representation and discards the raw messages**. Auto-compaction optimizes for token efficiency, not task fidelity.
- **Structured summary vs. stale raw context**: the central distinction of this task (see table below).

---

## Patterns & when to use them

### Continue vs. Resume vs. Fork

| | How it finds the session | Track an ID? | Use when |
|---|---|---|---|
| **Continue** | Most recent session in the current directory | No | App runs one conversation at a time; pick up after a process restart |
| **Resume** | A specific session ID you supply | Yes | Multiple sessions (e.g. one per user), or returning to a session that isn't the most recent |
| **Fork** | Copies an existing session's history into a **new** session ID; original untouched | Yes (parent + fork) | Try an alternative/risky path while keeping the option to go back |

### When to fork
- Explore a **risky or speculative path** without polluting the canonical session.
- Run **parallel sub-investigations** from a common starting state.
- Let a **sub-agent work on a copy** while the main agent continues on the original.
- Fork gets its **own new session ID**; the parent's ID and history stay unchanged → two independent sessions you can resume separately.

### State-management pattern (structured summaries)
- **Author explicit structured summaries at decision checkpoints** — you control what survives compaction rather than trusting a generic auto-summary.
- A good summary captures: `goal`, `completedSteps`, `pendingSteps`, `keyDecisions`, `assumptions`, `lastUpdated`.
- **Inject a summary in the system prompt or as the first labeled user turn** — never as an assistant turn.
- Structured summaries mitigate compaction risk; **pruning / re-confirming state** mitigates stale-context risk.

### Structured summary vs. stale raw context

| | Structured Summary | Stale Raw Context |
|---|---|---|
| What it is | Explicit, authored digest of key facts | Verbatim old messages never pruned |
| Risk | May omit edge-case details | Outdated decisions, superseded values, wrong state |
| Mitigation | Author summaries at decision checkpoints | Prune / re-confirm state before resuming old sessions |

### Resume across hosts / machines
Session files are **local to the machine that created them**. To resume elsewhere (CI, containers, serverless):
- **Attach a `SessionStore` / `session_store` adapter** so the SDK mirrors transcripts to your backend (lookup key derives from working directory → resume from a matching `cwd`).
- **Move the session file**: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` into a dir under `~/.claude/projects/` on the new host.
- **Or don't rely on resume at all**: capture the results (analysis, decisions, diffs) as application state and pass them into a *fresh* session's prompt — often more robust than shipping transcripts.

## Gotchas / exam traps

1. **Resuming old sessions without verifying assumptions** — a session from last week carries last week's worldview (code, APIs, decisions may have changed). Explicitly re-confirm critical assumptions (the `SessionSummary.assumptions` "verify if resuming after >24h" pattern) before letting the agent act.
2. **Relying on compaction to preserve critical state** — auto-compaction is token-efficient, not fidelity-preserving. Author structured summaries at checkpoints so *you* choose what survives.
3. **Using forks without tracking lineage** — always record `parentSessionId` with each fork so you can trace decisions to origin and clean up dead branches; unreconciled forks become orphaned context.
4. **Treating session ID as an opaque handle** — the ID guarantees a stable reference but NOT that model state matches your app state. Pair every ID with a metadata record.
5. **Injecting summaries as assistant turns** — belongs in the **system prompt** or the **first user turn** (clearly labeled). As an assistant turn it confuses the model about what it actually said → self-referential errors.
6. **Fork edits are real** — forking branches the conversation, not the filesystem; a forked agent's file writes affect the shared directory. Use file checkpointing to branch/revert files.
7. **`--continue` skips some sessions** — it deliberately skips background sessions, SDK/`-p`-created sessions, and sessions whose first prompt was `/loop` (unless you add those flags). Use `--resume <id>` to reach those.
8. **Cross-directory / same-machine only** — resume searches beyond the current project dir to find an ID (as of v2.1.223), but the session file must still exist on the current machine.

## Quick reference

### CLI (Claude Code)
| Command / flag | Meaning |
|---|---|
| `claude -c` / `claude --continue` | Continue most recent conversation in current directory |
| `claude -r "<session>"` / `claude --resume <id-or-name>` | Resume a session by ID or name (or show interactive picker) |
| `claude --session-id <uuid>` | Use a specific session ID for the conversation (must be a valid UUID) |
| `claude --resume abc123 --fork-session` | **Resume but create a NEW session ID instead of reusing the original** (use with `--resume` or `--continue`) |
| `claude -n "name"` / `claude --name` | Set a display name; resume later with `claude --resume <name>` |
| `/rename` | Change a session name mid-session |

### Agent SDK — resume & fork
| SDK detail | Python | TypeScript |
|---|---|---|
| Continue most recent | `continue_conversation=True` | `continue: true` |
| Resume specific session | `resume=session_id` (option on `query()`) | `resume: sessionId` (option on `query()`) |
| **Fork** | `fork_session=True` (with `resume=`) | `forkSession: true` (with `resume`) |
| Auto session-holding client | `ClaudeSDKClient` (each `.query()` continues same session; `receive_response()` to iterate) | *(none)* — pass `continue: true` per `query()` |
| Suppress transcript / stateless | `env: CLAUDE_CODE_SKIP_PROMPT_HISTORY` | `persistSession: false` |
| Options object | `ClaudeAgentOptions` | `Options` |

- **Reading the session ID**: on the result message — `session_id` field (`ResultMessage` in Python / `SDKResultMessage` in TS), present on every result regardless of success/error. Also available earlier on the init `SystemMessage` (TS: direct field; Python: nested in `SystemMessage.data`).
- **Resume AND fork both require a session ID.** Capture it first.
- **Enumerate/read sessions on disk**: TS `listSessions()` / `getSessionMessages()`; Python `list_sessions()` / `get_session_messages()`.
- Single-shot `query()` **raises after yielding an error result** — catch the error before resuming (e.g. recovering from `error_max_turns` / `error_max_budget_usd` with a higher limit).
- Session file path: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`.
- Note: the experimental **V2 session API** (`createSession()` with send/stream) was **removed** in TS Agent SDK 0.3.142 — use `query()` + session options.

### Context window / compaction & memory
- Compaction = summarize older turns + discard raw messages when nearing the token budget.
- CLI compaction controls: `/autocompact` (or `--autocompact <auto|tokens>`, e.g. `--autocompact 500k`) sets the auto-compact window for the session.
- **CLAUDE.md** (persistent instructions) and **auto memory** (`~/.claude/projects/<project>/memory/`, indexed by `MEMORY.md`) carry knowledge *across* sessions — each session still begins with a fresh context window. `MEMORY.md`: first 200 lines / 25KB loaded at session start.
- CLAUDE.md is delivered as a **user message after the system prompt**, not the system prompt itself → no strict compliance guarantee. Instructions given only in conversation may vanish after compaction; put durable instructions in CLAUDE.md.
- Subagents don't inherit the main conversation's auto memory — **except a fork**, which inherits the parent conversation and system prompt.

### Agent SDK positioning (context)
Agent SDK = library running the agent loop in your process (Python/TS). **Sessions** capability = "maintain context across exchanges, resume or fork later." Alternatives: Claude Code CLI (interactive), Client SDK (raw API, you build the loop), Managed Agents (hosted, Anthropic runs sandbox + sessions).
